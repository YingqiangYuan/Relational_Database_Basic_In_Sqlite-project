## § 4 — README co-write outline (English only)

Total length target: 250–500 words. English only regardless of the source repo's language(s). The publish skill walks the user through each section in order, asks the prompts one at a time, drafts the section in the user's voice, and confirms before locking.

### Section 1 — Project description

- Goal: Tell a passing reader, in 2–4 sentences, what this repo is and what it teaches.
- Length target: 50–80 words.
- Prompts:
  1. "In one sentence, what is this project?"
  2. "Who would care about it? (the audience — engineers learning SQL? data folks new to SQLAlchemy?)"
  3. "What's the simplest way to describe what someone learns from running these scripts?"

### Section 2 — Install & run

- Goal: Give a reader the exact command sequence from clone to first running output.
- Length target: 50–80 words.
- Prompts:
  1. "What's the minimum command sequence from a fresh clone to seeing output from one of the scripts?"
  2. "Does the reader need `mise` installed, or can they get by with just `uv`?"
  3. "Which script do you want them to run first? Why that one?"

### Section 3 — What I learned

- Goal: Three or four sentences in the user's voice on what they took away. This is the section that turns a clean repo into a portfolio piece — it's the *only* place a hiring reader sees real reflection.
- Length target: 80–120 words.
- Prompts:
  1. "What surprised you most when you worked through this?"
  2. "If a friend asked 'what was the point?', what would you say?"
  3. "What was the hardest part to internalize?"
  4. (Optional) "What's the one thing you now understand that you didn't before?"

### Section 4 (optional) — What's next

- Goal: Show the reader the user is still thinking past this artifact. Optional — drop if the user can't think of anything sincere.
- Length target: 30–60 words.
- Prompts:
  1. "If you spent another week on this, what would you add?"
  2. "Is there a related skill you want to absorb next?"

### Voice guardrails (apply during all sections)

- First-person past tense for what was built. Present tense for what the project is.
- Never write "this tutorial taught me…" or "in this project we…". If the user uses those phrases verbally, soften to "I built this to…".
- "I learned a lot" is filler — push for specifics.
- The draft must reflect the user's actual answers. Do **not** invent insight the user didn't supply.

## § 5 — Hostile-scan rules (for Audit mode)

The Audit assumes a hostile reader is scanning the repo with the question "did this come from a tutorial?" Each rule includes a severity hint.

### 🔴 HIGH RISK — fatal on detection

- **File-pattern flags.** Any of the following present is fatal:
  - `README-*.md` (any non-root README other than `README.md` itself)
  - `*-tutorial.*`, `*-course.*`
  - `docs/learn-this-project/` or `docs/learn-*/`
  - `docs/tutorials/` or any `docs/tutorial*` directory
  - `TICKET.md` (the course ticket card)
  - `.claude/skills/learn-this-project-{absorb,quiz,elevate,interview,demo,publish}/` (any of the six siblings)
  - `.claude/skills/lesson-smith*/` (any match)
  - `.claude/skills/write-agent-skill/`
- **README phrase flags.** In `README.md`, any of:
  - "this tutorial", "this course", "this lesson"
  - "in this project we", "let's learn", "we will explore", "we'll be"
  - "the mentor", "the instructor", "your task is"
  - "as a student", "we learned", "we covered"
  - First-person-plural learning prose anywhere in the file.
- **Residual directory flags.** Any `.claude/skills/learn-this-project-*` other than `learn-this-project-meta/`.

### 🟡 MEDIUM RISK — recoverable but visible

- **Commit-message phrase flags.** Same phrase set as the README — applied to commit subjects and bodies via `git log --all --format="%s%n%b"`. Plus "chore: setup", "chore: initial", "wip", or any imperative-mood subject that conflicts with the first-person past-tense convention established for this repo's commits.
- **Git ref flags.** Tags or branches whose names hint at the tutorial source:
  - `tutorial-base`, `from-tutorial`, `original`, `v0-from-course`, `course-start`, `lesson-*`
  - Detected by `git tag --list` + `git branch --all`.
- **Suspicious symmetry flags.** Identical comment banners across multiple files, identical docstring shapes (e.g., all ten `examples/s*.py` opening with the same 6-line block), or "obviously templated" boilerplate — a hostile reader spots this. The `examples/` directory in this specific repo has high symmetry by design (s1x mirrors s2x); flag it as a heuristic only, not a hard rule.
- **Hygiene-but-visible flags.**
  - `.idea/`, `__pycache__/`, `.venv/`, `*.egg-info/` committed.
  - `learn_this_project.egg-info/` specifically — this repo has it tracked; remove before publishing.

### 🔵 LOW RISK — cosmetic

- `.DS_Store` files committed.
- `.gitignore` missing common Python entries (`__pycache__/`, `*.egg-info/`, `.venv/`).
- Trailing whitespace, inconsistent line endings, or other formatter-grade issues.

### Audit honesty rule

If the repo passes (zero HIGH, near-zero MEDIUM), the skill should say so explicitly: "This repo passes hostile-scan. Safe to publish." If it doesn't, do not soften the finding count.
