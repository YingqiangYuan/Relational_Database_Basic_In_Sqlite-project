# 06 — Demo Playbook

> **Scope notes (set at meta-skill bootstrap).** This is a **teaching repo**, not a feature-rich product. The honest framing for any demo is *"here is a worked example for learners"*, not *"here is a portfolio app I built." Demoing it as the latter will undersell the candidate (the project is too small to carry that weight) AND undercut credibility (an interviewer will see the gap immediately).

## Wow features (priority order)

1. **The lesson sequence itself: `s01` → `s05`, all five CRUD verbs in five short scripts.** What lands: clarity. Each script is self-contained, well-commented, runs in seconds, and produces visible SQL + ASCII tables. The audience sees a complete miniature curriculum, not a code dump. Open `examples/s03_select_data.py` for the showpiece (most variety, most output).

2. **`echo=True` — the generated SQL is part of the lesson.** What lands: insight. Run any script and the SQL statements print right alongside the Python that produced them. For an audience that knows SQL but is new to ORMs/Core, this is the single most "ahh, that's what it does" moment. Use `s04_update_data.py` for max effect — three different UPDATEs become three visibly different SQL statements.

3. **The `print_table` helper + the docstring discipline.** What lands: taste. The audience sees that even a teaching repo has consistent conventions: shared formatting helper, three-block docstring style ("goal / mental model / why this choice"), section banners between concepts. This signals "I write code that's read by other people, not just by me."

## Recommended sequence

### 5-minute version

1. **(0:00) One-line frame.** "This is a teaching repo I built/maintain — five worked examples that walk a learner through the four CRUD verbs against SQLite, using SQLAlchemy 2.0 Core. I wrote it because I wanted to nail down the mental model before touching the ORM." Open the project root in your editor; show the `examples/` directory in the file tree.

2. **(0:30) Show the five-script structure.** Click through the file names in `examples/` so the numbering tells the story (`s01_create_table`, `s02_insert_data`, …). One sentence each. *Don't* open the empty `learn_this_project/` package or the placeholder READMEs.

3. **(1:30) Open `s03_select_data.py` and scroll to the docstring.** "Each script starts with this three-block layout: what the lesson is, the mental model, and why this design choice." Read 1–2 lines of the docstring aloud. Don't read the whole thing.

4. **(2:30) Run `s03` in the terminal.** Either `uv run python examples/s03_select_data.py` or activate-then-run. Wait for the output. Don't narrate while it runs.

5. **(3:00) Walk the output once it's done.** Point at the printed `CREATE TABLE`, `INSERT`, and `SELECT` SQL — "this is what the Python produced." Then point at the ASCII tables. "And this is what the helper renders. Same data, viewed two ways."

6. **(4:00) Land the close.** "What I'd do next: an ORM-based parallel set of lessons in `examples/v2/`, plus a real test suite — currently the test is 'I run it and read the output,' which is the right place to start but not the right place to stop." Close the editor.

### 15-minute version

1. **(0:00) One-line frame** (as above, 5-min step 1).
2. **(0:30) Repo tour.** Show `pyproject.toml` (deps + Python version), `mise.toml` (tasks), then `examples/`. Skip the empty package.
3. **(2:00) Open `s01_create_table.py`.** Walk the steps in order: engine (point at `:memory:` and `echo=True`), MetaData, Table definition with each column's constraint, `metadata.create_all`, `inspect()` verification. Tone: teaching, not selling.
4. **(5:00) Run `s01`.** Show the `CREATE TABLE` SQL and the empty-table render.
5. **(6:00) Open `s02_insert_data.py`.** Show single insert (`.values()` + `inserted_primary_key`) vs bulk insert (list of dicts). Note that the schema is redefined — say *why* (it's deliberate; `:memory:` is per-process AND repetition is pedagogy). This is a credibility moment — naming a non-DRY choice as deliberate is much stronger than hand-waving it.
6. **(8:00) Open `s03_select_data.py`.** Walk the five sub-lessons. Run it. Walk the output.
7. **(11:00) Open `s04_update_data.py`.** Highlight `users_table.c.age + 1` — the database does the math, not Python. Briefly mention `result.rowcount` as the safety habit.
8. **(13:00) Open `s05_delete_data.py`.** Just the DELETE-vs-DROP comment block at `:127–139`. The point is that you put it there.
9. **(14:00) Open `examples/utils.py`.** Show `print_table` is 35 lines, single-purpose, well-documented. Mention `CursorResult` is single-use — it's why the helper signature is what it is.
10. **(14:45) Close.** What's next: ORM lessons, multi-table with foreign keys, a real test suite, a real README.

## Do NOT show — explicit list

- **`learn_this_project/__init__.py`** — empty file. Showing it raises the question "what's in your package?" with the only honest answer being "nothing yet." Avoid the question.
- **`learn_this_project.egg-info/`** — auto-generated by editable install. Looks scratchy, signals nothing.
- **`README.md` and `README-ORIGINAL.md`** — both contain only the project title. A reader scanning for context finds nothing. Don't put either on screen.
- **`.venv/`, `__pycache__/`, `examples/__pycache__/`** — environment / bytecode caches. Standard but distracting in a file tree.
- **`uv.lock`** — only show this if asked (it answers "how do you pin?"). It's not a wow feature; opening it unprompted looks like padding.
- **`.idea/`** — JetBrains config. Personal, not part of the project.
- **The `git log` if it's in the room** — `init` → `add 5 examples` → `Use pretty table`. Honest history but reads like "I wrote this in a weekend." Better to talk about the work conceptually.
- **Any failed/exploratory script you may have locally** — if you have anything in `examples/` beyond `s01`–`s05` and `utils.py`, decide: ship it as a numbered lesson or move it out before the demo.

## Rehearsal questions (audience-role mode)

When practicing, have someone (or yourself out loud) ask these. They are the questions an actual viewer is most likely to fire:

1. **"Why SQLite and not Postgres?"** — Strong answer leads with "SQLite ships with Python, zero install" and acknowledges the dialect-quirk tradeoff.
2. **"Why Core, not the ORM?"** — Strong answer: "Core stays close to SQL; ORM concepts (Session, identity map, mapped classes) layer on top of fundamentals the learner doesn't have yet." Bonus: "I'd add an ORM parallel set of lessons next."
3. **"Where would you take this next?"** — Strong answer: tests + README first, then ORM parallel, then multi-table with foreign keys to introduce JOINs. (Order matters — leading with "I'd add JOINs" without addressing the missing test suite reads as misprioritized.)
4. **"What's the most surprising thing about SQLAlchemy you learned writing this?"** — Honest answer: pick one — "that `users_table.c.age > 25` returns a SQL expression node, not a boolean", or "that `inserted_primary_key` is the canonical way to get the auto-assigned id", or whatever genuinely surprised you.
5. **"If I were a new learner, what's the first script I should run, and why?"** — Strong answer: `s01_create_table.py`. It introduces the `engine → MetaData → Table → create_all` ladder and uses `inspect()` to confirm the table exists, which closes the loop visually on the very first run. Don't say `s03` even though it has the most variety — you'd be skipping the foundation.
