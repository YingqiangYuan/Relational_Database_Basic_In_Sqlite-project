# 06 — Demo Playbook

> **Scope notes (set at meta-skill bootstrap).** This is a **teaching repo**, not a feature-rich product. The honest framing for any demo is *"here is a worked example for learners"*, not *"here is a portfolio app I built." Demoing it as the latter will undersell the candidate (the project is too small to carry that weight) AND undercut credibility (an interviewer will see the gap immediately).

## Wow features (priority order)

1. **The two-series structure: `s11`–`s15` (raw SQL) and `s21`–`s25` (Core Expression).** What lands: pedagogy that matches how you'd actually teach this if you stopped to think. The audience sees that you walk a learner up the abstraction ladder *one rung at a time* — text, then code-that-generates-text — instead of throwing the abstraction at them and saying "trust me." Open `examples/README.md` first to set the frame, then `examples/s13_select_data.py` and `examples/s23_select_data.py` side-by-side to show the same lesson at two layers.

2. **`echo=True` in s2x — the generated SQL is part of the lesson.** What lands: insight. Run any s2x script and the SQL statements print right alongside the Python that produced them. For an audience that knows SQL but is new to Core, this is the single most "ahh, that's what it does" moment. Use `s24_update_data.py` for max effect — three different UPDATEs become three visibly different SQL statements. (And contrast with `s14_update_data.py`, where the SQL is in the source already and `echo` would be redundant.)

3. **The `print_table` helper + the docstring discipline.** What lands: taste. The audience sees that even a teaching repo has consistent conventions: one shared formatting helper that handles both raw-SQL and Core call shapes (because both return the same `CursorResult`), three-block docstring style ("goal / mental model / why this choice"), section banners between concepts, and `examples/README.md` as the on-ramp. This signals "I write code that's read by other people, not just by me."

## Recommended sequence

### 5-minute version

1. **(0:00) One-line frame.** "This is a teaching repo I built/maintain — ten worked examples in two parallel series that walk a learner through CRUD against SQLite. The first series teaches it as raw SQL via `sqlalchemy.text(...)`, the second teaches the same operations using SQLAlchemy Core Expression. I wrote it because I wanted to nail down both the SQL itself and the Pythonic way to compose it before touching the ORM." Open the project root in your editor; show the `examples/` directory in the file tree.

2. **(0:30) Show the two-series structure.** Click through the file names in `examples/` so the numbering tells the story (`s11_*` through `s15_*`, then `s21_*` through `s25_*`). One sentence framing each series. *Don't* open the empty `learn_this_project/` package or the placeholder repo-root READMEs. Briefly open `examples/README.md` so they see the on-ramp doc exists.

3. **(1:30) Open `s13_select_data.py` and `s23_select_data.py` side-by-side.** "Each script starts with the same three-block docstring: what the lesson is, the mental model, and why this design choice." Read 1–2 lines aloud. Point at one SELECT in each file — note that the raw-SQL `text("SELECT * FROM users WHERE age > :min_age")` becomes `select(users_table).where(users_table.c.age > 25)` in Core. Same lesson, two layers.

4. **(2:30) Run `s23` in the terminal.** `uv run python examples/s23_select_data.py`. Wait for the output. Don't narrate while it runs.

5. **(3:00) Walk the output once it's done.** Point at the printed `SELECT` statements — "this is what `select(users_table).where(...)` generated, thanks to `echo=True`." Then point at the ASCII tables. "And this is the shared `print_table` helper that works for both series."

6. **(4:00) Land the close.** "What I'd do next: a third ORM-based series `s31`–`s35`, plus a real test suite — currently the test is 'I run it and read the output,' which is the right place to start but not the right place to stop." Close the editor.

### 15-minute version

1. **(0:00) One-line frame** (as above, 5-min step 1).
2. **(0:30) Repo tour.** Show `pyproject.toml` (deps + Python version), `mise.toml` (tasks), then `examples/README.md` (the on-ramp doc explaining why scripts, why SQLite, why SQLAlchemy, and the two-series structure). Skip the empty package.
3. **(2:00) Open `s11_create_table.py`.** Walk the steps in order: engine (note that `echo=True` is intentionally OFF here because the SQL is right there in the source), the `text("CREATE TABLE IF NOT EXISTS users (...)")` block, `engine.begin()` + `conn.execute`, `inspect()` verification. Tone: teaching, not selling.
4. **(4:00) Open `s21_create_table.py` and show the same lesson in Core.** Engine with `echo=True`, MetaData, Table definition with each column's constraint, `metadata.create_all`, `inspect()` verification. The point: same SQL, different way of expressing it.
5. **(6:00) Run `s21`.** Show the `CREATE TABLE` SQL that Core generated alongside the empty-table render.
6. **(7:00) Open `s22_insert_data.py`.** Show single insert (`insert(users_table).values(...)` + `inserted_primary_key`) vs bulk insert (list of dicts). Note that the schema is redefined — say *why* (it's deliberate; `:memory:` is per-process AND repetition is pedagogy). Mention the s1x equivalent uses `text("INSERT ... VALUES (:name, ...)")` and `result.lastrowid`. This is a credibility moment — naming a non-DRY choice as deliberate is much stronger than hand-waving it.
7. **(9:00) Open `s23_select_data.py`.** Walk the five sub-lessons. Run it. Walk the output.
8. **(11:30) Open `s24_update_data.py`.** Highlight `users_table.c.age + 1` — the database does the math, not Python. Briefly mention `result.rowcount` as the safety habit. Note that the s14 raw-SQL version does the same thing with `text("UPDATE users SET age = age + 1")` — the lesson is identical, only the layer differs.
9. **(13:00) Open `s25_delete_data.py`.** Just the DELETE-vs-DROP comment block near the end. The point is that you put it there.
10. **(14:00) Open `examples/utils.py`.** Show `print_table` is 35 lines, single-purpose, well-documented, and works for both series because both `text(...)` and `select(...)` return the same `CursorResult`. Mention `CursorResult` is single-use — it's why the helper signature is what it is.
11. **(14:45) Close.** What's next: an ORM series `s31`–`s35`, multi-table with foreign keys, a real test suite, a real repo-root README.

## Do NOT show — explicit list

- **`learn_this_project/__init__.py`** — empty file. Showing it raises the question "what's in your package?" with the only honest answer being "nothing yet." Avoid the question.
- **`learn_this_project.egg-info/`** — auto-generated by editable install. Looks scratchy, signals nothing.
- **Repo-root `README.md` and `README-ORIGINAL.md`** — both contain only the project title. A reader scanning for context finds nothing. Don't put either on screen. (Note: `examples/README.md` is fine to show — it's substantial.)
- **`.venv/`, `__pycache__/`, `examples/__pycache__/`** — environment / bytecode caches. Standard but distracting in a file tree.
- **`uv.lock`** — only show this if asked (it answers "how do you pin?"). It's not a wow feature; opening it unprompted looks like padding.
- **`.idea/`** — JetBrains config. Personal, not part of the project.
- **The `git log` if it's in the room** — short history reading like "I wrote this in a weekend or two". Better to talk about the work conceptually.
- **Any failed/exploratory script you may have locally** — if you have anything in `examples/` beyond `s11`–`s15`, `s21`–`s25`, `README.md`, and `utils.py`, decide: ship it as a numbered lesson or move it out before the demo.

## Rehearsal questions (audience-role mode)

When practicing, have someone (or yourself out loud) ask these. They are the questions an actual viewer is most likely to fire:

1. **"Why SQLite and not Postgres?"** — Strong answer leads with "SQLite ships with Python, zero install" and acknowledges the dialect-quirk tradeoff. Point at `examples/README.md` § "Why SQLite?" for the long form.
2. **"Why raw SQL first, then Core — and not the ORM?"** — Strong answer: "Raw SQL teaches the learner what SQL actually looks like and what bound parameters are. Core teaches them how to *compose* SQL in code without losing the safety net. ORM concepts (Session, identity map, mapped classes) layer on top of fundamentals neither of the first two layers requires — adding it before the first two would reverse the learning gradient. The plan is to add an ORM series `s31`–`s35` next."
3. **"Where would you take this next?"** — Strong answer: tests + repo-root README first, then ORM series `s31`–`s35`, then multi-table with foreign keys to introduce JOINs. (Order matters — leading with "I'd add JOINs" without addressing the missing test suite reads as misprioritized, especially now that there are two series that need to stay in lockstep.)
4. **"What's the most surprising thing about SQLAlchemy you learned writing this?"** — Honest answer: pick one — "that `users_table.c.age > 25` returns a SQL expression node, not a boolean", or "that `lastrowid` (s1x) and `inserted_primary_key` (s2x) recover the auto-assigned id at different abstraction levels", or whatever genuinely surprised you.
5. **"If I were a new learner, what's the first script I should run, and why?"** — Strong answer: read `examples/README.md` first to get the rationale, then run `s11_create_table.py`. It uses raw SQL — the most familiar starting point for anyone who's seen SQL before — and the `inspect()` verification closes the loop visually on the very first run. From there, walk s12→s15 in order before crossing over to s21. Don't recommend starting at s23 even though it has the most variety — you'd be skipping the foundation.
