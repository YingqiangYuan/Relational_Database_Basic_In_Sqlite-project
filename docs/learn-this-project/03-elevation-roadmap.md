# 03 — Elevation Roadmap

> **Scope notes (set at meta-skill bootstrap).** This is a teaching repo, not a product. "Elevation" here means "what would a senior engineer add to make this a *better teaching artifact* and a more honest portfolio piece" — NOT "production-grade observability + auto-scaling". Production-pattern items appear, but are framed as *concepts the learner should learn* rather than *gaps the project must fill*.

## Executive view (highest leverage first)

1. **Add a runnable test that imports + executes each example script.** Single fixture, no pytest plugin sprawl. Catches the "I edited s03 and forgot to re-run it" class of regression.
2. **Add a real `README.md`.** The current one is a single header. A reader landing on the repo cannot tell what they're looking at, what to install, or what to run.
3. **Introduce SQLAlchemy ORM (declarative_base + Session) as `s06`–`s10`.** Same `users` table, same operations, ORM style — so the learner sees the *same lesson twice*, the second time with the layer that's actually used in real apps.
4. **Add `s00_setup.py` (or extend the runbook) showing file-based SQLite + persistence across runs.** `:memory:` is great for the lesson but hides one of the most important real-world questions: where does the data go between runs?
5. **Add foreign keys + a second table (`posts` referencing `users`).** Single-table CRUD is a half-truth; relational means relationships, and a learner who only sees one table will struggle the moment they meet a JOIN.

## Upgrade areas

### Test depth and coverage

- **Current state.** No test directory; no `pytest` config; no CI. The only "test" is "did the script print what I expected when I ran it." (`02-runbook.md` says this explicitly.)
- **Senior-engineer target state.** A `tests/` directory with one `test_examples.py` that subprocess-invokes each `examples/sNN_*.py` and asserts exit code 0 and that the stdout contains the expected ASCII-table headers (e.g., `--- All rows ---`, `--- Top 2 oldest users ---`). Wired into a GitHub Actions workflow that runs `mise install && mise run inst && pytest -q` on push.
- **Alternatives considered.**
  - **A: subprocess-based smoke tests (above).** Pro: tests the script as a learner would actually run it. Con: catches "did anything print?" but not "did the right rows print." Tradeoff: low maintenance, low specificity.
  - **B: refactor each script to expose a `main()` and import-test the rendered output as a string.** Pro: precise assertions on output text. Con: forces every example into a function shape that's worse pedagogically (script-as-narrative is the current strength). Tradeoff: better signal, worse teaching code.
  - **C: extract logic into the `learn_this_project/` package and unit-test that.** Pro: idiomatic Python testing. Con: the lessons live in the scripts; gutting them defeats the project's purpose.
- **Knowledge prerequisites.** `pytest` basics (fixtures, `capsys`, `subprocess.run`); GitHub Actions YAML; `uv` in CI (`uv sync` + `uv run pytest`).
- **Suggested learning path.** (1) `pytest` getting-started docs → (2) `pytest`'s `capsys` and `tmp_path` → (3) GitHub Actions "Python testing" example workflow → (4) cache `uv` between CI runs (`actions/cache` keyed on `uv.lock`).

### Documentation and onboarding

- **Current state.** `README.md` and `README-ORIGINAL.md` each contain only `# learn_relational_database_basic_in_sqlite-project`. `CLAUDE.md` documents the toolchain for Claude but not for a human reader. The lessons themselves are well-commented inside each script — there's no top-level "what is this project, who is it for, how do I read it" page.
- **Senior-engineer target state.** A `README.md` that, in this order: (1) one-paragraph pitch ("a Python learner's introduction to relational databases via SQLAlchemy 2.0 Core on SQLite — five worked examples, one per CRUD verb"); (2) prerequisites and 4-line install; (3) a numbered list linking each `examples/sNN_*.py` to a one-line description; (4) "what you'll learn" outcomes list; (5) where to go next (ORM, file-backed SQLite, multi-table). Optionally a `docs/` index.
- **Alternatives considered.**
  - **A: rich README with embedded sample output and a small architecture diagram.** Pro: portfolio-quality. Con: drift risk — sample output ages with code changes.
  - **B: README is the index, narrative lives in `docs/lessons/sNN.md`.** Pro: lets each lesson have prose alongside code. Con: doubles the writing load and the drift surface.
  - **C: keep code-only, write nothing.** Pro: zero overhead. Con: the project is invisible to anyone who isn't already in the repo.
- **Knowledge prerequisites.** Markdown formatting; choosing a README structure (the "github standard README" template is a common reference).
- **Suggested learning path.** (1) Read `https://www.makeareadme.com` for the structural template → (2) study a few SQLAlchemy tutorial repos for tone → (3) write the README in one sitting; iterate after the first reader feedback.

### API / contract design (= teaching API)

- **Current state.** Each script redefines the schema (engine, MetaData, Table, columns) at the top — ~25 lines of repeated setup before the lesson begins. This is *deliberate* non-DRY for pedagogy: the learner re-sees the same shape five times. But once a learner has internalized the setup, the repetition becomes noise and obscures the lesson.
- **Senior-engineer target state.** A second-pass version of the lessons under `examples/v2/` (or `examples/orm/`) that imports a shared `schema.py` and `engine.py` from `learn_this_project/`. The original `examples/` stays as the "first read." This gives the learner a literal demonstration of the refactor: "here's the version that teaches the shape, here's the version that uses it."
- **Alternatives considered.**
  - **A: single shared module from day one.** Pro: clean code. Con: defeats the pedagogical reason for repetition. Bad tradeoff for *this* project.
  - **B: keep `examples/` as-is, add ORM-based `examples/sNN_orm.py` that does NOT share setup either (same pedagogical pattern).** Pro: consistent learning model. Con: no shared-module lesson at all. Reasonable.
  - **C: add a `learn_this_project.schema` module and have the original scripts continue to redefine inline (so `schema.py` is for the curious learner, not for the lessons).** Pro: zero disruption. Con: the package gets used only if the learner browses `learn_this_project/`. Status-quo-ish.
- **Knowledge prerequisites.** Python packaging basics (relative imports, why `examples/` isn't packaged); when DRY helps and when it hurts.
- **Suggested learning path.** (1) Read SQLAlchemy 2.0 ORM tutorial → (2) write `learn_this_project/schema.py` defining the same `users` table → (3) duplicate `s02–s05` into `s02_orm.py–s05_orm.py` using `Session` and mapped classes; compare line-for-line.

### Data layer (relationships, migrations, persistence)

- **Current state.** One table (`users`). All databases are `:memory:` — data vanishes per process. No migrations.
- **Senior-engineer target state.** (a) Add `posts` table with `author_id INTEGER REFERENCES users(id)`, demonstrating one-to-many with INSERT, SELECT-with-JOIN, and ON DELETE CASCADE behavior. (b) Add `s00_setup_file.py` showing `sqlite:///./data/learning.db` and what happens on re-runs (the data is still there). (c) Optionally a `s99_migrations.py` introducing Alembic in the simplest possible way (one revision adding a column).
- **Alternatives considered.**
  - **A: SQLite + raw migrations (hand-written DDL files).** Pro: dialect-agnostic, simpler than Alembic for one revision. Con: doesn't transfer to real-world workflows where Alembic is the norm.
  - **B: Alembic from day one.** Pro: real-world. Con: heavy concept (env.py, versions/, branches) for a beginner repo.
  - **C: skip migrations entirely, add only relationships + persistence.** Pro: keeps scope tight. Con: leaves a major real-world topic untouched.
- **Knowledge prerequisites.** Foreign key semantics in SQLite (PRAGMA foreign_keys ON is required!); JOIN syntax; ON DELETE CASCADE vs RESTRICT vs SET NULL; basics of schema migration.
- **Suggested learning path.** (1) SQLite docs on foreign keys (note the `PRAGMA foreign_keys = ON` gotcha) → (2) SQLAlchemy 2.0 tutorial section "Working with related data" → (3) Alembic "tutorial" page (skim end-to-end before writing anything) → (4) a single autogenerated revision adding a column.

### Developer experience (DX)

- **Current state.** No `mise run` task to execute the lessons. To run `s01`, you type `uv run python examples/s01_create_table.py`. There's no `make all`, no `mise run lesson 03`. No `.envrc`, no auto-activation.
- **Senior-engineer target state.** `mise.toml` adds `[tasks.lesson]` accepting an arg: `mise run lesson 03` runs `s03_*.py`. Optionally `mise run lessons-all` runs `s01..s05` in sequence. A short `[tasks.repl]` opens an `ipython` (or `python -i`) shell with `users_table` and `engine` already imported.
- **Alternatives considered.**
  - **A: `Makefile`.** Pro: universal. Con: contradicts the project's existing `mise`-first stance.
  - **B: dedicated CLI inside `learn_this_project/__main__.py` (`python -m learn_this_project run 03`).** Pro: introduces packaging-as-CLI as a learning artifact. Con: more code, more moving parts.
  - **C: leave it; `uv run python …` is fine.** Pro: zero work. Con: friction every single time.
- **Knowledge prerequisites.** `mise` task syntax (positional args, `usage` field); maybe `argparse` if doing the CLI alternative.
- **Suggested learning path.** (1) `mise` tasks docs → (2) add one task and try it → (3) decide if you want a CLI or stop at task aliases.

### Observability (logging instead of `echo=True`)

- **Current state.** SQL is printed via SQLAlchemy's `echo=True`, which routes through Python's `logging` under the hood but emits to stdout/stderr without a structured format.
- **Senior-engineer target state.** A small `learn_this_project.logging` module that configures the `sqlalchemy.engine` logger with a clean format (level, statement preview, parameters) and a knob (env var `LOG_SQL=0/1`) to silence it for non-teaching uses. Surfaces the lesson "echo=True is a shortcut; here's how it actually works."
- **Alternatives considered.**
  - **A: keep `echo=True` everywhere.** Pro: simplest. Con: when this project is used as a copy-paste seed for a real app, the `echo=True` follows it into production-noise territory.
  - **B: `logging.basicConfig(level=logging.INFO, ...)` once at the top of each script.** Pro: standard. Con: still couples display to log level.
  - **C: structured logging via `structlog`.** Pro: real-world pattern. Con: introduces a new dep and a new concept for a beginner repo. Probably overkill.
- **Knowledge prerequisites.** Python `logging` (handlers, formatters, named loggers); the difference between `logger.info` and `print`; environment-driven config.
- **Suggested learning path.** (1) Python `logging` HOWTO → (2) SQLAlchemy "Configuring Logging" docs → (3) replace `echo=True` in one script and verify the output is identical / better.

### Security and threat model

- **Current state.** All inputs in the example scripts are hardcoded. The script `s03_select_data.py:111–117` calls out the SQL-injection lesson explicitly: "never f-string user input into a WHERE clause; let SQLAlchemy bind it."
- **Senior-engineer target state.** Add `s99_sql_injection.py` that takes user input via `input(...)` and shows two implementations side-by-side: the unsafe `f"WHERE name = '{name}'"` (with `text(...)`) vs. the safe `where(users_table.c.name == name)`. Show the actual SQL emitted in both cases (`echo=True` already on). The audience walks away knowing what *parameter binding* visually looks like.
- **Alternatives considered.**
  - **A: write a paragraph in the README and stop.** Pro: zero scope creep. Con: the project's strength is "show, don't tell"; an unrun script is weaker than a runnable one.
  - **B: a Jupyter notebook that's interactive.** Pro: interactive. Con: adds a notebook tooling stack.
- **Knowledge prerequisites.** What "bound parameters" mean; SQLAlchemy's `text()` escape hatch and when not to use it.
- **Suggested learning path.** (1) OWASP "SQL injection" cheatsheet → (2) SQLAlchemy `text()` docs → (3) write the contrast script.
