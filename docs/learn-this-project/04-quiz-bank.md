# 04 — Quiz Bank

> **Scope notes.** All items are drawn from `examples/` (both the s1x raw-SQL series and the s2x Core Expression series), `examples/README.md`, `examples/utils.py`, and `pyproject.toml` / `mise.toml`. Nothing comes from the empty `learn_this_project/` package.

## How these questions are designed (read this first)

These are **not** flash-card prompts where one fact maps to one answer. They are guided **discussion questions** with two goals:

1. **Show the student where to look in the repo to answer the question themselves**, so they leave with a navigation skill, not a memorized fact.
2. **Probe whether they understand the *reason* a choice was made**, not whether they can recite that the choice exists.

A good question is one or two sentences and is open enough to let the student wander. A good answer is three to five sentences, names the specific files and line numbers a learner should open to verify the answer, and ends with the *why*. If an answer is a single fact, the question was too narrow — split it or rewrite it as a "walk me through…" prompt.

Tags: `knowhow` (why-questions), `runbook` (setup/run/workflow), `convention` (project-wide patterns), `deps` (dependencies/versions), `mech` (how-the-code-actually-works walk-throughs), `series` (questions comparing s1x vs s2x).

Difficulty: `easy` (the answer is mostly recall plus one observation), `medium` (the answer requires connecting two files or explaining one design choice), `hard` (the answer requires reasoning across the whole repo or about a topic the code doesn't state outright).

## Setup, environment, and the toolchain

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A new contributor just cloned this repo and asks you what they need to type to get a working Python environment. Where would you point them, and what would you tell them about how the toolchain layers fit together?
  - **A:** Point them at `mise.toml` at the repo root — that one file declares both the runtime versions (`python = "3.12"`, `uv = "latest"`) and the project tasks. The two commands they need are `mise run venv-create` (which runs `uv venv` to create `.venv/`) and `mise run inst` (which runs `uv sync --all-extras` to install everything in `pyproject.toml`). The reason this project layers `mise` on top of `uv` is that `mise` answers *both* "which Python version should I be on?" and "what commands should I run?", so a new contributor doesn't have to memorize separate `pyenv` / `uv` / `make`-style stacks. `CLAUDE.md` documents these commands for AI tooling, but `mise.toml` is the source of truth.

- **Q-002** [tag: deps, difficulty: easy]
  - **Q:** If a teammate asked you "what does this project actually depend on, and why is each one here?", which file would you open and how would you explain the choices?
  - **A:** Open `pyproject.toml` — its `[project].dependencies` block lists exactly two third-party packages: `SQLAlchemy>=2.0.33,<3.0.0` and `prettytable>=3.15.1,<4.0.0`. SQLAlchemy is the database toolkit; it's pinned to 2.0+ because the example code uses 2.0-style `select() / insert() / update() / delete()` constructors and the explicit `text(...)` execution form. `prettytable` is used by `examples/utils.py` to render result rows as ASCII tables so output is consistent across all ten example scripts. The conservative upper bounds (`<3.0`, `<4.0`) allow minor and patch updates but block surprise major-version upgrades.

- **Q-003** [tag: deps, difficulty: medium]
  - **Q:** SQLAlchemy is pinned to `>=2.0.33,<3.0.0`. Walk through why the 2.0 lower bound matters for this specific codebase, and where in the code you can see the evidence.
  - **A:** The 2.0 lower bound is load-bearing because both teaching styles in `examples/` use APIs that are 2.0-only. In the s2x series you can see the unified constructor form (`select(users_table)`, `insert(users_table)`, etc.) — e.g. `examples/s23_select_data.py:80`. In the s1x series you can see the explicit `text(...)` wrapper required to execute raw SQL in 2.0 — e.g. `examples/s13_select_data.py:67–71`. Earlier SQLAlchemy 1.x would accept raw strings without `text()` and used different `query()`-style APIs, so loosening the lower bound below 2.0 would silently break every script in the repo.

- **Q-004** [tag: runbook, difficulty: medium]
  - **Q:** Suppose you want to run `examples/s13_select_data.py` from a fresh shell. Talk through what you'd type and *why* each step is needed, given the way this project is structured.
  - **A:** The simplest invocation is `uv run python examples/s13_select_data.py` from the repo root. `uv run` matters here because the project's dependencies (SQLAlchemy, prettytable) live in the project venv created by `mise run venv-create` / `mise run inst`; `uv run` automatically resolves to that venv so you don't have to manually activate it. Each script is fully self-contained — it creates its own in-memory SQLite database, defines its own table, seeds its own data — so order doesn't matter and you can run any script as a one-off. If `uv` is not yet installed, you'd start one level earlier with `mise run venv-create` and `mise run inst`, which is documented in `02-runbook.md`.

- **Q-005** [tag: convention, difficulty: medium]
  - **Q:** The `examples/` directory holds the lesson, but `pyproject.toml`'s setuptools config only packages `learn_this_project*`. What is the practical consequence of that, and what does it tell you about the intent of the `learn_this_project/` package?
  - **A:** The practical consequence is that `pip install`-ing the wheel of this project from outside the repo would give you the empty `learn_this_project/` package and zero example scripts — the lessons only exist if you have the repo cloned. That's fine for a teaching repo, since the lessons are meant to be *read in their source form*, not imported. The empty `learn_this_project/__init__.py` exists because setuptools' `find` block needs *something* to discover for the build to succeed (see `pyproject.toml:10–14`). The probable forward-looking intent is to eventually host shared helpers there, after which example scripts could replace `from utils import print_table` with `from learn_this_project import print_table`.

## Why scripts (not a GUI), why SQLite, why SQLAlchemy

- **Q-006** [tag: knowhow, difficulty: medium]
  - **Q:** This is a course about SQL, yet every lesson is delivered as a Python script that runs end-to-end. If a student asked "why aren't we just pasting SQL into DBeaver?", what would you say, and what file would you point them at for the long-form answer?
  - **A:** Point them at `examples/README.md` § "Why Python scripts, and not a database GUI?" — the README's whole job is to set up this framing before they open any code. The three reasons it gives are: (a) GUIs don't enforce step order, so if you forget which step you're on the database is silently in the wrong state; (b) GUIs make "start over from a clean slate" tedious — you'd have to drop and recreate tables manually; (c) scripts freeze the lesson in a reproducible artifact, which is the property you actually need when you're learning. Every script uses `sqlite:///:memory:` so the database is wiped on every run and there's no stale state to fight.

- **Q-007** [tag: knowhow, difficulty: medium]
  - **Q:** Why does a *learn-relational-databases* course use SQLite specifically, instead of PostgreSQL or MySQL? Where in the repo is this rationale laid out, and which property of SQLite is the one that matters most for teaching?
  - **A:** The rationale lives in `examples/README.md` § "Why SQLite?". The decisive property is that SQLite needs **no server**: it's a Python-stdlib-included library, it stores the database as either a single file or pure RAM (`:memory:`), and there are no ports, daemons, or credentials to manage. Postgres or MySQL would impose a setup tax — install the server, create a user, open a port — that has nothing to do with learning SQL. SQLite also speaks standard enough SQL that the `CREATE TABLE`/`INSERT`/`SELECT`/`UPDATE`/`DELETE` the student learns here will transfer almost unchanged to a server database later.

- **Q-008** [tag: knowhow, difficulty: medium]
  - **Q:** Open `examples/README.md` and find the section on SQLAlchemy. In your own words, how would you explain to a learner *why* a course about SQL routes everything through a Python library instead of calling `sqlite3` directly?
  - **A:** The README's argument boils down to three points. First, in the Python ecosystem SQLAlchemy is the de-facto database toolkit, so the student will meet it again in any serious application — better to start with it than to unlearn `sqlite3` later. Second, SQLAlchemy is *layered* — its bottom layer lets you send raw SQL strings (the s1x series uses this), and a higher layer lets you build SQL out of Python expressions (the s2x series uses that) — so the same library carries the student from "I just want to run a query" to "I want to compose queries in code". Third, even when you write raw SQL, going through SQLAlchemy handles the unglamorous bits — connection management, transactions, safe parameter binding, dialect normalization — so the lessons can stay focused on SQL itself.

- **Q-009** [tag: knowhow, difficulty: easy]
  - **Q:** The README mentions the ORM exists but the course doesn't use it. What's the reasoning given, and what should a learner take away from that aside?
  - **A:** `examples/README.md` § "A quick word on the ORM" frames the ORM as solving a *related* problem (avoiding scattered raw SQL, making data access structured), but with extra concepts — mapped classes, sessions, identity map, lazy loading — that this beginner course deliberately skips. The takeaway is not "ORMs are bad", it's "you're not ready for them yet; you need to feel tables and SQL first". The implicit promise is that once a learner is comfortable with both s1x and s2x, the ORM is the natural next step. So when you hit that section, file the term away and don't go googling for SQLAlchemy ORM tutorials mid-course.

## The two series: s1x (raw SQL) vs s2x (Core Expression)

- **Q-010** [tag: series, difficulty: easy]
  - **Q:** The `examples/` folder has two parallel five-script series. What's the naming pattern, and how do you know at a glance which script teaches which topic in which style?
  - **A:** The pattern is `sNN_<verb>_<topic>.py`, where the first digit is the **style** (1 = raw SQL via `text(...)`, 2 = SQLAlchemy Core Expression) and the second digit is the **CRUD step** (1=create, 2=insert, 3=select, 4=update, 5=delete). So `s14_update_data.py` is "update taught with raw SQL", and `s24_update_data.py` is "the same update lesson, taught with Core". A two-digit numeric prefix also makes them sort in lesson order in any file browser. The README's "Suggested reading order" section makes this explicit: README first, then s11→s15, then s21→s25.

- **Q-011** [tag: series, difficulty: medium]
  - **Q:** Why does the course deliberately teach raw SQL *before* SQLAlchemy Core, instead of jumping straight to the Pythonic API? What would go wrong pedagogically if the order were reversed?
  - **A:** The argument from `examples/README.md` is that before a learner can appreciate an abstraction *over* SQL, they need to have seen SQL itself with their own eyes. If you walk a beginner straight into `select(users_table).where(users_table.c.age > 25)`, they often can't tell which parts of that Python correspond to which parts of the SQL it generates — it just feels like magic. By starting with `text("SELECT * FROM users WHERE age > :min_age")` in s13, the learner builds a mental model of *what SQL looks like*, and then when s23 shows the Core form they can map it back. The s2x scripts also enable `echo=True` precisely so the generated SQL is visible — closing the loop.

- **Q-012** [tag: series, difficulty: medium]
  - **Q:** If the two series teach exactly the same SQL operations, why does the course bother showing both styles instead of picking one? Frame your answer in terms of what's gained at each layer.
  - **A:** Each layer teaches a different lesson. The raw-SQL layer (s11–s15) teaches *what SQL looks like* and how to bind parameters safely — these are universal skills that transfer to any language and any database. The Core layer (s21–s25) teaches *why hand-written SQL doesn't scale* in real applications: when you have a hundred queries that share a table but differ in tiny ways, building each one as a Python expression makes them composable, conditionally extensible, and type-aware in ways raw strings can't be. Skipping s1x would leave the student unable to read other people's SQL; skipping s2x would leave them unable to write SQL the way their future workplace probably writes it. The README's "Why hand-written SQL is rare in real applications" section makes this argument explicitly.

- **Q-013** [tag: series, difficulty: medium]
  - **Q:** Pick the INSERT lesson (s12 raw SQL vs s22 Core). What stays the same between the two versions, and what's different about how you express it?
  - **A:** What stays the same is the *shape* of the operation: both files insert a single row first, then bulk-insert via list-of-dicts, then read back to verify. What changes is the language used to express the INSERT — in `s12_insert_data.py:73–80` you write the SQL as a string `text("INSERT INTO users (name, age, email) VALUES (:name, :age, :email)")` and pass a parameter dict; in `s22_insert_data.py:75–82` you write `insert(users_table).values(name=..., age=..., email=...)`, no SQL string in sight. The new-row id is also accessed differently — `result.lastrowid` (a SQLite/DBAPI cursor attribute) in s12, `result.inserted_primary_key` (a SQLAlchemy-level abstraction that works across dialects) in s22.

- **Q-014** [tag: series, difficulty: hard]
  - **Q:** A junior dev shows you a feature request that needs ten variations of "fetch users, possibly filtered by city, possibly sorted, possibly limited". They want to know whether to write each variation as raw SQL or as Core. Using the README's reasoning, walk through how you'd advise them.
  - **A:** This is exactly the case the README's "Why hand-written SQL is rare in real applications" section anticipates. If you wrote each variation as raw SQL you'd end up with ten near-identical strings scattered through the codebase, and conditional pieces ("only add `WHERE city = :city` if a city was provided") force awkward string concatenation that tempts people into f-string interpolation — which is how SQL injection bugs are born. Core Expression lets the same query be built up incrementally: start with `stmt = select(users_table)`, then `if city: stmt = stmt.where(users_table.c.city == city)`, then `if sort: stmt = stmt.order_by(...)`. The bound-parameter safety is automatic, the same query *object* can be reused, and misspelling a column name is a Python error instead of a database error at runtime. Tell them to use Core for this.

## Engines, connections, transactions

- **Q-015** [tag: mech, difficulty: medium]
  - **Q:** Every script begins with `engine = create_engine("sqlite:///:memory:")` (or with `echo=True` in s2x). Walk through what `create_engine` actually returns, when it talks to the database, and what the URL is communicating.
  - **A:** `create_engine` returns an `Engine` object — SQLAlchemy's *handle* to the database, often described in the docstrings as "a phone number that knows how to call the database". It does **not** open a connection at construction time; the first real connection is opened lazily when you run a statement (e.g. inside `with engine.begin() as conn:`). The URL `sqlite:///:memory:` decodes as "SQLite dialect, database lives entirely in RAM, no file backing", which is why every script starts from a clean slate. You can see the construction at `examples/s11_create_table.py:63` (no `echo`) and `examples/s21_create_table.py:61` (`echo=True`).

- **Q-016** [tag: convention, difficulty: medium]
  - **Q:** Why do the scripts use `with engine.begin() as conn:` for INSERT/UPDATE/DELETE but `with engine.connect() as conn:` for SELECT? Walk through the difference and the reason for the split.
  - **A:** `engine.begin()` does three things in one line — opens a connection, starts a transaction, and commits the transaction automatically when the `with` block exits cleanly (or rolls back if an exception is raised inside). `engine.connect()` just opens a connection without an explicit transaction block. The scripts use `begin()` for writes (e.g. `examples/s12_insert_data.py:73`, `s22:75`) because writes need to be committed for the change to stick; they use `connect()` for reads (e.g. `examples/s13_select_data.py:67`, `s23:80`) because a SELECT has nothing to commit. Following this split is the canonical convention every example honors.

- **Q-017** [tag: knowhow, difficulty: medium]
  - **Q:** `echo=True` appears on the engine in the s2x series but is absent in s1x. Why the asymmetry, and what does the flag actually do?
  - **A:** `echo=True` makes SQLAlchemy print every SQL statement it sends to the database before executing it. In the s2x series this is part of the lesson — the student wrote Python (`select(users_table).where(users_table.c.age > 25)`), and seeing the generated SQL is how they verify what their Python compiled to. In the s1x series the SQL is already plain text in the source file (`text("SELECT * FROM users WHERE age > :min_age")`), so echoing it would print the same string they're staring at — pure noise. The asymmetry is intentional, and the comments at `examples/s11_create_table.py:54–60` explicitly call it out so a reader doesn't think it was forgotten.

- **Q-018** [tag: mech, difficulty: medium]
  - **Q:** When you write `with engine.begin() as conn:` and an exception is raised inside the block, what happens to the database changes the block had already made? Where would you look in the example scripts to see this contract being relied on?
  - **A:** The transaction is **rolled back** — every change made inside the block is undone, leaving the database in the state it had before the `with` started. That is precisely why every write in the example scripts uses `engine.begin()` instead of `engine.connect()` plus a manual `conn.commit()`: it's safer by default. You don't see the rollback being exercised explicitly in the examples (they don't raise on purpose), but the contract is what lets the scripts say "do all my database work in this block and the right thing happens automatically" — e.g., the multi-row UPDATE at `examples/s14_update_data.py:85–93` is one of several writes that would be cleanly rolled back if an exception were raised mid-block.

## Schema: how the `users` table is described

- **Q-019** [tag: series, difficulty: medium]
  - **Q:** Both `s11` and `s21` end up with the same `users` table in the database, but they describe its schema in completely different ways. Open both files and walk through how each one expresses the same four columns.
  - **A:** `s11_create_table.py:94–102` writes the schema as a triple-quoted SQL string — `CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, age INTEGER, email TEXT UNIQUE)` — wrapped in `text(...)` and executed once. `s21_create_table.py:73, 102–109, 122` builds the same schema through Python objects: `MetaData()` (a registry), then `Table("users", metadata, Column("id", Integer, primary_key=True), Column("name", String, nullable=False), Column("age", Integer), Column("email", String, unique=True))`, then `metadata.create_all(engine)` which emits the actual `CREATE TABLE IF NOT EXISTS` against the database. The generated SQL is essentially identical; the difference is whether the *description* of the schema lives as a string or as Python objects.

- **Q-020** [tag: knowhow, difficulty: medium]
  - **Q:** The `email` column is declared `UNIQUE` in the raw-SQL version and `unique=True` in the Core version. Why is this rule placed at the database level rather than enforced in application code?
  - **A:** Putting `UNIQUE` (or `unique=True`) on the column makes the **database itself** reject any insert that would duplicate an existing email — see `s11_create_table.py:99` and `s21_create_table.py:108`. That matters because application code is fallible: a bug, a race condition, or a forgotten check could let a duplicate slip through. A database-level constraint is a backstop that cannot be bypassed by buggy application code, which is the whole reason it exists. The same argument applies to `NOT NULL` on `name` — see Q-021.

- **Q-021** [tag: knowhow, difficulty: medium]
  - **Q:** `name` is declared `NOT NULL` (raw SQL) / `nullable=False` (Core), but `age` is left nullable. Talk through why the schema makes that distinction.
  - **A:** A user without a name is a logic error worth catching at the database boundary — there's no meaningful application state where you'd want to store a row with no name, so encoding "must have a value" in the schema catches the bug at the earliest possible moment. Age is different: a user might legitimately not have provided their age, and silently failing the insert in that case would be wrong. The choice is a small but real piece of data modeling, and it's also a teaching moment — see the comments in `examples/s11_create_table.py:73–87` and `s21_create_table.py:90–96` that spell out the reasoning so the learner sees it as a deliberate decision rather than a default.

- **Q-022** [tag: mech, difficulty: medium]
  - **Q:** Both `s11` and `s21` follow their CREATE TABLE with `inspect(engine)` calls. Why? What does that buy a learner over just running a `SELECT *` to confirm the table exists?
  - **A:** `inspect(engine)` opens a read-only view of the database's **schema** — its list of tables, the columns of each table, their types and nullability. The example scripts use it at `s11:131–137` and `s21:131–137` to print the table list plus per-column metadata as a sanity check. A bare `SELECT *` would prove the table exists (the query wouldn't error), but `inspect()` lets the learner see *the table's shape* — column names, types, and nullability — which is the concrete thing they just created. It closes the loop on lesson 1 in a way a learner can read and confirm.

## Bound parameters and SQL injection safety

- **Q-023** [tag: knowhow, difficulty: medium]
  - **Q:** Open `examples/s13_select_data.py` and find the `WHERE age > :min_age` example. Explain to a junior dev who suggests using `f"WHERE age > {min_age}"` why their suggestion is dangerous, and what the colon-prefix form actually does differently.
  - **A:** The danger is **SQL injection**. With `f"WHERE age > {min_age}"` the value is glued into the SQL string before the database ever sees it; if `min_age` came from user input — a web form, an API parameter — a hostile value like `25 OR 1=1` could rewrite the rest of the statement. The colon-prefix form `:min_age` is a **bound parameter**: SQLAlchemy passes the SQL string and the value to the database separately, and the database driver treats the value strictly as data — it can't change the SQL's structure. You can see the dict-of-parameters being passed as the second argument to `execute` at `s13_select_data.py:106–110`. The comment block right above that example calls this out explicitly because it's the single most important safety habit to internalize.

- **Q-024** [tag: series, difficulty: medium]
  - **Q:** In the s1x series you write `:name` placeholders explicitly. In the s2x series the bound parameters are invisible. Walk through what the s2x code is doing under the hood and why the safety guarantee still holds.
  - **A:** When you write `users_table.c.age > 25` in `s23_select_data.py:118`, that expression isn't compared in Python — it returns a SQL expression object. When `conn.execute(stmt)` runs, SQLAlchemy compiles the expression into SQL and emits the literal `25` as a **bound parameter**, exactly the same way `:min_age` would in raw SQL. So the safety property is identical; the Core layer just hides the parameter naming because it can generate the binding for you. If you turn on `echo=True` (which the s2x series does) you can see in the printed SQL that values are sent as `?` placeholders with the actual values logged separately — that's the bound-parameter mechanism made visible.

## INSERT

- **Q-025** [tag: mech, difficulty: medium]
  - **Q:** In `s12_insert_data.py`, you insert one row and then immediately print `result.lastrowid`. What does that attribute represent, and why does the script make a point of showing it to the learner?
  - **A:** `result.lastrowid` is the id the database picked for the row that was just inserted — see `examples/s12_insert_data.py:73–80`. Because the schema declares `id` as `INTEGER PRIMARY KEY`, SQLite auto-assigns the next available integer; the application doesn't supply an id at insert time. Surfacing it answers the very common beginner question "how do I find out the id of the row I just created?" — typically because the next thing you want to do is reference the row (insert a related row, show it back to the user, etc.). The s2x counterpart at `s22_insert_data.py:80–82` uses `result.inserted_primary_key`, which is the database-agnostic version of the same idea.

- **Q-026** [tag: mech, difficulty: hard]
  - **Q:** `s12` and `s22` both demonstrate bulk insert by passing a *list of dicts* as the second argument to `conn.execute`. What does SQLAlchemy actually do under the hood when you call it that way, and what's the difference between the single-row and bulk-insert call shapes?
  - **A:** Passing a list of dicts as the second argument tells SQLAlchemy to run the same statement once per dict, letting the database driver batch the work efficiently — see `s12_insert_data.py:97–104` and `s22_insert_data.py:95–104`. The call shape differs in two visible ways: (1) for a single row you put the data on the statement itself (via `text(...)`'s `:name` placeholders + a parameter dict in s12, or `.values(...)` in s22), but for bulk insert you omit `.values()` and pass the data as the second positional arg; (2) the single-row form exposes the new id (`lastrowid` / `inserted_primary_key`), while the bulk form does not surface a per-row id in the same way. Mixing the two call shapes (e.g., calling `.values()` *and* passing a list) silently does the wrong thing.

- **Q-027** [tag: knowhow, difficulty: medium]
  - **Q:** Neither script supplies an `id` value on insert. Walk through why that works at the database level and what would change if the schema didn't have an integer primary key.
  - **A:** Because `id` is declared `INTEGER PRIMARY KEY` (raw SQL) / `Integer, primary_key=True` (Core), SQLite treats it as an alias for the table's internal rowid and auto-assigns the next available integer on insert — see `examples/s11_create_table.py:74–82`. If `id` were declared without `PRIMARY KEY` or with a non-integer type, the column would be `NULL` by default and inserts would fail because the column declares `NOT NULL` (or, if it didn't, you'd insert genuine `NULL`s). On other databases the auto-assignment mechanism is different — Postgres uses `SERIAL` / `IDENTITY`, MySQL uses `AUTO_INCREMENT` — which is one of the dialect details SQLAlchemy abstracts over.

## SELECT

- **Q-028** [tag: series, difficulty: medium]
  - **Q:** Compare how `s13` and `s23` express "users older than 25". Each is a short snippet — walk through both, name the file and line, and explain what's substantively different between them.
  - **A:** In `s13_select_data.py:106–110` you write `text("SELECT * FROM users WHERE age > :min_age")` and pass `{"min_age": 25}` as the parameter dict. In `s23_select_data.py:118–120` you write `select(users_table).where(users_table.c.age > 25)` — no SQL string, no parameter dict. The substantive differences are (a) in s23 the comparison is a Python expression on a column object, so the SQL is *generated* rather than typed; (b) the bound parameter is emitted automatically in s23, whereas in s13 you wrote `:min_age` explicitly. Both produce the same underlying SQL and both bind the `25` as a parameter, so the safety guarantee is identical.

- **Q-029** [tag: mech, difficulty: easy]
  - **Q:** A SQLAlchemy `Result` from `conn.execute(...)` exposes `.all()`, `.first()`, `.scalar()`, and direct iteration. When would you reach for each, and where in the example scripts can you see them used?
  - **A:** `.all()` materializes the whole result as a list — best when you expect a small number of rows. `.first()` returns just the first row (or `None` if there were no rows) — best when you expect at most one match, like a lookup by primary key. `.scalar()` returns the first column of the first row — best when the query returns a single value, like a count or a single name. Direct iteration (`for row in result:`) streams rows one at a time without loading them all — best when the result might be large. All four are demonstrated at `examples/s13_select_data.py:142–161` and `examples/s23_select_data.py:155–172`.

- **Q-030** [tag: knowhow, difficulty: medium]
  - **Q:** In `s23`, when you write `users_table.c.age > 25`, that expression doesn't evaluate as a Python boolean — it produces a SQL expression object. Why does that matter, and what's the most common conceptual mistake a beginner makes here?
  - **A:** It matters because the comparison is **not executed in Python**; it returns an object describing a comparison that will be performed by the database, row by row, when the query runs. See the inline comment at `examples/s23_select_data.py:110–113`. The common beginner mistake is to think of it as a regular Python comparison and try to combine it with Python `and`/`or` — which would force a boolean evaluation and either silently lose the SQL semantics or raise. The correct way to combine SQL expressions is with SQLAlchemy's `and_(...)` / `or_(...)` or the bitwise `&` / `|` operators, which preserve the "this is a SQL fragment" intent.

- **Q-031** [tag: mech, difficulty: easy]
  - **Q:** Both scripts show "the two oldest users" as `ORDER BY age DESC LIMIT 2`. What's the canonical pattern in each style, and what does each piece contribute?
  - **A:** Raw SQL at `s13_select_data.py:123–125`: `text("SELECT * FROM users ORDER BY age DESC LIMIT 2")`. Core at `s23_select_data.py:133–139`: `select(users_table).order_by(users_table.c.age.desc()).limit(2)`. The two pieces are independent — `ORDER BY age DESC` sorts the rows from highest to lowest age, and `LIMIT 2` keeps only the first two. Without ordering first the "limit" would pick rows in unspecified order, so the combination "order then limit" is the standard recipe for top-N queries.

## UPDATE

- **Q-032** [tag: knowhow, difficulty: easy]
  - **Q:** The module docstrings of `s14` and `s24` both lead with a "rule of UPDATE". What is it, and what's the failure mode if you ignore it?
  - **A:** The rule is: **always include a WHERE clause unless you really mean to modify every row in the table**. The failure mode is silent: an UPDATE with no WHERE clause rewrites the whole table, and the database happily does it because that is what the statement asked for. The docstrings emphasize this at the very top so the rule is the first thing the learner reads — see `examples/s14_update_data.py:12–15` and `examples/s24_update_data.py:12–15`. In practice the habit pairs with "run a SELECT with the same WHERE first to preview what you're about to change", which the comments reinforce as the operational safety move.

- **Q-033** [tag: mech, difficulty: medium]
  - **Q:** Both scripts check `result.rowcount` after each UPDATE. What does that number tell you, and how should a careful developer use it in real code?
  - **A:** `result.rowcount` reports how many rows the database actually modified — see `examples/s14_update_data.py:85–93` and `examples/s24_update_data.py:99–106`. A `rowcount` of 0 means the WHERE matched nothing; that's not an error, but it's a strong signal that either the row you meant to update doesn't exist (legitimate "not found") or your WHERE is wrong (a bug). A careful developer logs the rowcount, alerts on unexpected zeros, and in some cases turns "I updated zero rows when I expected one" into an application-level error. The example scripts model the habit by always printing it.

- **Q-034** [tag: knowhow, difficulty: hard]
  - **Q:** Walk through why `UPDATE users SET age = age + 1` is the right way to give everyone a birthday, instead of selecting each user's age in Python, adding 1, and updating with the new value. Use the example code to ground your answer.
  - **A:** The single-statement form at `s14_update_data.py:128–130` (`UPDATE users SET age = age + 1`) and `s24_update_data.py:145–148` (`update(users_table).values(age=users_table.c.age + 1)`) lets the **database** do the arithmetic in one round-trip and atomically per row. The Python-side read-modify-write alternative would be two round-trips (read all ages, write them back), and worse, it's unsafe under concurrency: if another transaction also modifies the row between your read and your write, you'd silently overwrite their change. Letting the database compute `age + 1` from the column's *current* value sidesteps both problems. This is a microcosm of a broader principle — when the database can do the computation, prefer that over moving data into Python and back.

- **Q-035** [tag: convention, difficulty: medium]
  - **Q:** `s14` and `s24` both define a local `print_all(label)` helper instead of putting that helper in `utils.py`. What's the reasoning, and what does that tell you about the project's approach to factoring shared code?
  - **A:** `print_all` captures the module-local `engine` and `users_table`, so to lift it into `utils.py` you'd have to give it a more complex signature (passing the engine and the table) without any reuse benefit — the function exists only inside these two scripts. See `examples/s14_update_data.py:57–65` and `s24_update_data.py:71–79`. The broader principle visible here is: factor a helper only when factoring it *simplifies* the call sites. Sometimes the cleanest design is a small, locally-defined helper rather than a more generic shared one. `print_table` in `utils.py`, by contrast, is genuinely reused across all ten scripts and benefits from being centralized.

## DELETE

- **Q-036** [tag: knowhow, difficulty: easy]
  - **Q:** `s15` and `s25` end with `DELETE` (no WHERE) — the dangerous form — and then explicitly contrast it with `DROP TABLE`. What's the difference, and why does the course bother making the distinction?
  - **A:** `DELETE` with no WHERE removes every **row** in the table but leaves the **schema** intact — the table still exists, it's just empty (see `examples/s15_delete_data.py:122–135` and `examples/s25_delete_data.py:128–141`). `DROP TABLE` (in Core: `users_table.drop(engine)`) removes the table itself, schema and all — after a DROP you'd have to re-run `CREATE TABLE` before any further query against that table would work. The course makes the distinction because beginners frequently conflate the two and they have different operational consequences: a stray DELETE-without-WHERE is recoverable by re-inserting data, but a stray DROP requires re-creating the schema first.

- **Q-037** [tag: convention, difficulty: medium]
  - **Q:** Both DELETE scripts urge running a `SELECT` with the same WHERE first before running the DELETE. Why is this advice given as a *habit* rather than something automated in the code?
  - **A:** Because there's no general-purpose way to automate it — every DELETE has a different WHERE, and only the developer knows what "the same query" means. The comments at `examples/s15_delete_data.py:97–110` and `examples/s25_delete_data.py:106–117` spell it out: "run the same query as a SELECT first to preview what would be deleted" — phrased as "measure twice, cut once". The habit moves the failure mode from "I deleted the wrong rows and now I have to restore from backup" to "I noticed the SELECT showed unexpected rows and stopped before running the DELETE". Once committed, a DELETE has no application-level undo, which is exactly why the preview matters.

## Presentation: `utils.py` and `print_table`

- **Q-038** [tag: mech, difficulty: medium]
  - **Q:** Every script's output goes through `print_table` from `examples/utils.py`. Walk through what that function actually does and why each example chose to route output through it instead of `print(row)`.
  - **A:** `print_table` is defined at `examples/utils.py:25` and takes a SQLAlchemy `CursorResult` plus an optional title. It reads the column names from `result.keys()`, builds a `prettytable.PrettyTable`, left-aligns columns (`table.align = "l"`, line 48 — the default is centered, which is harder to scan), iterates the cursor adding one ASCII row per database row, and prints the result with an optional `--- title ---` banner. Routing every example through this helper makes the output of all ten scripts visually consistent, so a learner moving from `s13` to `s23` doesn't get distracted by formatting differences. Raw `print(row)` is used only in the "iter" sub-lessons of `s13` and `s23`, where seeing the raw tuple is the point.

- **Q-039** [tag: knowhow, difficulty: hard]
  - **Q:** The docstring of `print_table` calls out that a `CursorResult` is "single-use". What does that mean, and what would a learner have to do if they wanted to both pretty-print *and* re-iterate the rows?
  - **A:** A SQLAlchemy `Result` is a forward-only cursor — once you've iterated it (which `print_table` does on `examples/utils.py:53`) the caller cannot read it again. See the docstring at `utils.py:30–34`. If you needed both behaviors, you'd materialize the result first by calling `.all()`, which gives you a regular Python list you can pass to `print_table` once and then iterate again afterwards. The example scripts never need this — they print and move on — but it's a gotcha worth knowing because at first it looks like the result "disappeared".

- **Q-040** [tag: mech, difficulty: medium]
  - **Q:** Both raw-SQL calls (`conn.execute(text(...))`) and Core calls (`conn.execute(select(...))`) return objects that `print_table` accepts without modification. Why does one helper work for both styles?
  - **A:** Because both call shapes return the same underlying type: a SQLAlchemy `CursorResult`. The type carries `.keys()` (column names) and is iterable over rows regardless of whether the SQL was written as a string or built as a Core Expression. That's a deliberate property of SQLAlchemy's API — `conn.execute(...)` always returns the same `Result` shape — and it's what lets `utils.py` stay a 35-line module shared by ten teaching scripts without branching on the call style.

## Conventions and design rationale

- **Q-041** [tag: convention, difficulty: medium]
  - **Q:** Why does every script in `s12–s15` and `s22–s25` re-declare the schema and re-seed the data at the top, instead of factoring that setup into a shared module? Frame your answer in terms of who the audience is.
  - **A:** The duplication is **deliberate non-DRY**. The audience is a beginner, and beginners benefit from seeing the same shape (`engine → schema → seed → demonstrate`) over and over until it's automatic — factoring would obscure the pattern just when the learner is trying to internalize it. There's also a hard technical reason: `:memory:` SQLite databases don't persist across processes, so `s13` literally cannot share state with `s12` even if you wanted it to. Each script is therefore a self-contained, re-runnable artifact you can open in any order. The convention is documented in `01-knowhow-inventory.md` § "Conventions" rule 2.

- **Q-042** [tag: convention, difficulty: easy]
  - **Q:** Open any example script and look at how comments are written. What's the rule for what a comment should say and what it shouldn't, and where does this rule pay off most?
  - **A:** The rule is "explain *why*, not *what*" — the code already states what it does, so the comment's job is to explain the design intent. For example, `metadata.create_all(engine)` doesn't need a comment that says "this creates the table"; what it gets is a comment explaining *why this is the moment Python finally talks to the database* (see `examples/s21_create_table.py:113–122`). The rule pays off most where a learner would otherwise misread the code — for instance, `users_table.c.age > 25` looks like a Python comparison, so the comment block at `s23_select_data.py:110–117` exists to head off that misreading.

- **Q-043** [tag: convention, difficulty: easy]
  - **Q:** Where in the repo would you look first to learn the intended reading order of the example scripts? Why is the reading order important here when the scripts are technically independent?
  - **A:** Look at `examples/README.md` § "Suggested reading order": README first, then `s11` → `s12` → `s13` → `s14` → `s15`, then `s21` → `s22` → `s23` → `s24` → `s25`, then `utils.py` if curious. The order is important even though the scripts are independent because the *lessons* build on each other — bound parameters are introduced in s12 and assumed thereafter, the SELECT consumption styles introduced in s13 are reused in s23, and the entire reason s2x makes sense as the second pass is that you've already seen what raw SQL looks like in s1x. Reading in the wrong order won't break anything technically, but it'll feel like things keep being introduced in the wrong place.

- **Q-044** [tag: knowhow, difficulty: hard]
  - **Q:** If you wanted to convert the lessons from in-memory SQLite to a real file on disk, walk through what would change and why this matters as a teaching choice.
  - **A:** You'd change the URL from `sqlite:///:memory:` to `sqlite:///./learning.db` (three slashes, then a relative or absolute file path). The next run would start from the previous run's state — that's what changes the experience. The teaching choice to stay in-memory is deliberate: it guarantees every script starts from a clean slate, which means the output a learner sees matches the output the README promises. If you switched to a file, a half-completed lesson would leave the database in a weird state and the next run's output would look "wrong" through no fault of the learner. For real applications you'd of course want persistence; for *learning* you want repeatability.

- **Q-045** [tag: knowhow, difficulty: medium]
  - **Q:** Looking at the project as a whole — `examples/README.md`, two parallel script series, a tiny `utils.py`, and almost no test code — what's the project's *teaching philosophy*? What would change about the code if it were teaching a different kind of audience (say, working developers)?
  - **A:** The teaching philosophy is "feel one verb at a time, in two styles, with repeated shape, on a clean database every run". The repetition (each script re-declares the schema), the self-contained `:memory:` setup, the on-ramp README, and the two parallel series all support a learner who needs to *internalize* a small set of patterns before they meet variations. For working developers you'd compress this radically — one consolidated script with conditional branches, real persistence, an ORM example, a tests folder, maybe even a migration story — because that audience doesn't need the shape repetition and would find it tedious. The current shape is optimized for beginners, and the absence of "professional" affordances like tests or CI is itself a design choice, not an oversight (see `03-elevation-roadmap.md` for what "next-level" would look like).
