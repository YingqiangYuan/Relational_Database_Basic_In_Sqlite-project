## Engines, connections, transactions

- **Q-011** [tag: mech, difficulty: easy]
  - **Q:** What database URL do the example scripts use, and what does it mean?
  - **A:** `sqlite:///:memory:` — SQLite dialect, database lives in RAM only, vanishes when the process exits.
  - **Source:** `examples/s01_create_table.py:61`

- **Q-012** [tag: knowhow, difficulty: medium]
  - **Q:** Why use an in-memory SQLite database for the lessons instead of a file?
  - **A:** Each run starts from a clean slate with no file paths or cleanup to manage; perfect for learning where stale data is more confusing than helpful.
  - **Source:** `examples/s01_create_table.py:17–23`

- **Q-013** [tag: mech, difficulty: easy]
  - **Q:** What does `echo=True` on `create_engine(...)` do?
  - **A:** Makes SQLAlchemy print every SQL statement it sends to the database — used here as a teaching aid.
  - **Source:** `examples/s01_create_table.py:58–61`

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** What's the difference between `engine.connect()` and `engine.begin()`?
  - **A:** `engine.connect()` opens a connection without a transaction block; `engine.begin()` opens a connection AND a transaction that auto-commits on clean exit (rolls back on exception).
  - **Source:** `examples/s02_insert_data.py:17–27`, `examples/s03_select_data.py:20–24`

- **Q-015** [tag: convention, difficulty: medium]
  - **Q:** When do the example scripts use `engine.begin()` vs `engine.connect()`?
  - **A:** `engine.begin()` for writes (INSERT/UPDATE/DELETE) so changes commit automatically; `engine.connect()` for reads (SELECT) since there's nothing to commit.
  - **Source:** `examples/s02_insert_data.py:75`, `examples/s03_select_data.py:80`

- **Q-016** [tag: knowhow, difficulty: medium]
  - **Q:** Does `create_engine(...)` actually open a connection to the database?
  - **A:** No. It returns a handle ("phone number"); the first real connection happens lazily when a statement is executed.
  - **Source:** `examples/s01_create_table.py:48–52`

## Schema: MetaData, Table, Column

- **Q-017** [tag: mech, difficulty: easy]
  - **Q:** What is `MetaData` in SQLAlchemy?
  - **A:** A registry that remembers every `Table` defined against it, so calls like `metadata.create_all(engine)` know what to create.
  - **Source:** `examples/s01_create_table.py:65–73`

- **Q-018** [tag: mech, difficulty: easy]
  - **Q:** What four columns does the `users` table have, and what types?
  - **A:** `id` Integer (PK), `name` String (NOT NULL), `age` Integer (nullable), `email` String (UNIQUE).
  - **Source:** `examples/s01_create_table.py:102–109`

- **Q-019** [tag: knowhow, difficulty: medium]
  - **Q:** Why is `email` declared `unique=True` in the table definition?
  - **A:** So the database itself rejects duplicate emails — the invariant is enforced at the DB level even if application code is buggy.
  - **Source:** `examples/s01_create_table.py:97–101`

- **Q-020** [tag: knowhow, difficulty: medium]
  - **Q:** Why is `name` declared `nullable=False` but `age` left nullable?
  - **A:** A user without a name is a logic error worth catching early; a user without a known age is plausible (they didn't share it), so `age` defaults to nullable.
  - **Source:** `examples/s01_create_table.py:90–96`

- **Q-021** [tag: mech, difficulty: easy]
  - **Q:** What does `metadata.create_all(engine)` actually do?
  - **A:** Issues `CREATE TABLE IF NOT EXISTS ...` for every `Table` registered on this MetaData against the engine.
  - **Source:** `examples/s01_create_table.py:114–122`

- **Q-022** [tag: mech, difficulty: medium]
  - **Q:** How does `s01` verify the table actually got created in the database?
  - **A:** It uses `inspect(engine)` and prints `inspector.get_table_names()` plus column metadata; then runs an empty `select(users_table)` through `print_table` as a second sanity check.
  - **Source:** `examples/s01_create_table.py:131–149`

- **Q-023** [tag: convention, difficulty: medium]
  - **Q:** Each example script redefines the entire schema from scratch. Why?
  - **A:** Two reasons: (1) `:memory:` databases don't persist across processes so each script must rebuild; (2) re-seeing the same shape five times is deliberate pedagogy.
  - **Source:** `examples/s02_insert_data.py:42–49`, `docs/learn-this-project/01-knowhow-inventory.md` § "Conventions"

- **Q-024** [tag: knowhow, difficulty: medium]
  - **Q:** Why does the project use SQLAlchemy Core (the `Table` API) instead of the ORM?
  - **A:** Core stays close to raw SQL while being Pythonic, so beginners can see the SQL their Python becomes; ORM adds Session/identity-map concepts that aren't needed yet.
  - **Source:** `examples/s01_create_table.py:25–30`

## INSERT

- **Q-025** [tag: mech, difficulty: easy]
  - **Q:** Which file teaches single-row insert?
  - **A:** `examples/s02_insert_data.py`, around lines 75–82.
  - **Source:** `examples/s02_insert_data.py:75`

- **Q-026** [tag: mech, difficulty: easy]
  - **Q:** Does `insert(users_table).values(...)` send the SQL to the database?
  - **A:** No — it just builds and returns a Python statement object. The SQL is sent only when `conn.execute(stmt)` is called.
  - **Source:** `examples/s02_insert_data.py:67–71`

- **Q-027** [tag: mech, difficulty: medium]
  - **Q:** How does the script find out the auto-assigned `id` of a freshly inserted row?
  - **A:** `result.inserted_primary_key` on the value returned by `conn.execute(...)`.
  - **Source:** `examples/s02_insert_data.py:80–82`

- **Q-028** [tag: mech, difficulty: medium]
  - **Q:** How do you bulk-insert many rows in one call without writing a Python `for` loop?
  - **A:** Pass a list of dicts as the second argument: `conn.execute(insert(users_table), [{...}, {...}, {...}])`. No `.values()` on the statement when doing it this way.
  - **Source:** `examples/s02_insert_data.py:95–103`

- **Q-029** [tag: knowhow, difficulty: medium]
  - **Q:** Why do the inserts not specify an `id` value?
  - **A:** Because `id` is `Integer + primary_key=True`, SQLite auto-assigns the next available value as `INTEGER PRIMARY KEY` (auto-increment).
  - **Source:** `examples/s02_insert_data.py:67–74`

- **Q-030** [tag: mech, difficulty: hard]
  - **Q:** Name two visible differences in shape between the single-insert pattern and the executemany pattern in `s02`.
  - **A:** (1) Single uses `.values(...)` on the statement; executemany passes the data as the second arg to `execute(...)`. (2) Single returns `inserted_primary_key` on a single result; executemany doesn't expose it the same way.
  - **Source:** `examples/s02_insert_data.py:75–104`

## SELECT

- **Q-031** [tag: mech, difficulty: easy]
  - **Q:** What is the SQLAlchemy 2.0 way to write `SELECT * FROM users`?
  - **A:** `select(users_table)` — then `conn.execute(stmt)` to run it.
  - **Source:** `examples/s03_select_data.py:80–84`

- **Q-032** [tag: mech, difficulty: easy]
  - **Q:** How do you select only specific columns instead of `SELECT *`?
  - **A:** Pass column objects to `select(...)`: e.g., `select(users_table.c.name, users_table.c.age)`.
  - **Source:** `examples/s03_select_data.py:97–101`

- **Q-033** [tag: mech, difficulty: easy]
  - **Q:** What is `users_table.c`?
  - **A:** A namespace for the table's columns (`c` stands for "columns"); `users_table.c.name` means the `name` column of `users`.
  - **Source:** `examples/s03_select_data.py:95–96`

- **Q-034** [tag: mech, difficulty: easy]
  - **Q:** How do you add a WHERE clause to a SELECT?
  - **A:** Chain `.where(condition)` on the select; the condition uses Python comparison operators on column objects (e.g., `users_table.c.age > 25`).
  - **Source:** `examples/s03_select_data.py:118–120`

- **Q-035** [tag: knowhow, difficulty: medium]
  - **Q:** Does `users_table.c.age > 25` evaluate as a Python boolean?
  - **A:** No — it returns a SQL expression object that becomes part of a WHERE clause. The comparison runs server-side, row by row, when the query executes.
  - **Source:** `examples/s03_select_data.py:111–113`

- **Q-036** [tag: knowhow, difficulty: medium]
  - **Q:** Why does using column expressions in WHERE clauses prevent SQL injection?
  - **A:** SQLAlchemy emits the value as a *bound parameter* rather than interpolating it into the SQL string, so user input can't change the SQL structure.
  - **Source:** `examples/s03_select_data.py:115–117`

- **Q-037** [tag: mech, difficulty: easy]
  - **Q:** How do you sort a SELECT result by `age` descending and keep only the top 2 rows?
  - **A:** `select(users_table).order_by(users_table.c.age.desc()).limit(2)`.
  - **Source:** `examples/s03_select_data.py:133–138`

- **Q-038** [tag: mech, difficulty: easy]
  - **Q:** What does `.all()` do on a SQLAlchemy `Result`?
  - **A:** Materializes the cursor into a Python list of all rows. Best when the result is small enough to fit in memory.
  - **Source:** `examples/s03_select_data.py:78–79`, `:147`

- **Q-039** [tag: mech, difficulty: medium]
  - **Q:** When would you use `.first()` over `.all()`?
  - **A:** When you expect at most one match (e.g., lookup by primary key) and want `None` on miss instead of an empty list.
  - **Source:** `examples/s03_select_data.py:147–149`

- **Q-040** [tag: mech, difficulty: medium]
  - **Q:** What does `.scalar()` return?
  - **A:** The first column of the first row (or `None`). Handy for queries that return a single value (a count, a single name, etc.).
  - **Source:** `examples/s03_select_data.py:150–152`

- **Q-041** [tag: knowhow, difficulty: medium]
  - **Q:** Why prefer `for row in result:` iteration over `result.all()` for very large queries?
  - **A:** Iteration streams rows one at a time, so you don't load the entire result set into memory.
  - **Source:** `examples/s03_select_data.py:152–154`

## UPDATE

- **Q-042** [tag: mech, difficulty: easy]
  - **Q:** What is the canonical UPDATE pattern shown in `s04`?
  - **A:** `update(users_table).where(...).values(...)` — `where` selects which rows, `values` sets the new column values.
  - **Source:** `examples/s04_update_data.py:88–95`

- **Q-043** [tag: knowhow, difficulty: easy]
  - **Q:** What's the single most important rule the docstring of `s04` emphasizes about UPDATE?
  - **A:** Always include a WHERE clause unless you really mean to modify every row — UPDATE without WHERE silently changes the entire table.
  - **Source:** `examples/s04_update_data.py:12–15`

- **Q-044** [tag: mech, difficulty: easy]
  - **Q:** What does `result.rowcount` tell you after an UPDATE?
  - **A:** How many rows the database actually modified. `0` is a hint that your WHERE matched nothing.
  - **Source:** `examples/s04_update_data.py:96–98`

- **Q-045** [tag: knowhow, difficulty: medium]
  - **Q:** Why pass `users_table.c.age + 1` to `.values()` instead of reading the value, adding 1 in Python, and writing back?
  - **A:** It's one round-trip instead of two, AND the database performs the increment atomically per row — safe under concurrent writes.
  - **Source:** `examples/s04_update_data.py:140–144`

- **Q-046** [tag: mech, difficulty: medium]
  - **Q:** Why does `s04` define a local `print_all(label)` helper instead of putting it in `utils.py`?
  - **A:** It depends on the module-local `engine` and `users_table`, so factoring it out would force a bigger helper signature without a reuse benefit.
  - **Source:** `examples/s04_update_data.py:71–80`, `docs/learn-this-project/01-knowhow-inventory.md` § "s04 — Gotchas"

- **Q-047** [tag: mech, difficulty: medium]
  - **Q:** In `s04`'s "update users under 30 to YOUNGSTER" step, how many rows are affected and which?
  - **A:** Two rows — Bob (25) and Dave (19). Alice (30) is not strictly less than 30, and Carol (41) is older.
  - **Source:** `examples/s04_update_data.py:118–127`

## DELETE

- **Q-048** [tag: mech, difficulty: easy]
  - **Q:** What is the canonical DELETE pattern in `s05`?
  - **A:** `delete(users_table).where(...)` — same shape as UPDATE minus `.values()`.
  - **Source:** `examples/s05_delete_data.py:87–96`

- **Q-049** [tag: knowhow, difficulty: easy]
  - **Q:** What's the safest WHERE filter to use when deleting a single row?
  - **A:** Filter by primary key (`where(users_table.c.id == N)`); a PK match is at most one row, so there's no risk of deleting neighbours.
  - **Source:** `examples/s05_delete_data.py:88–92`

- **Q-050** [tag: knowhow, difficulty: medium]
  - **Q:** What "preview" habit does `s05` recommend before running a real DELETE?
  - **A:** Run a SELECT with the same WHERE clause first to see exactly what would be removed — "measure twice, cut once".
  - **Source:** `examples/s05_delete_data.py:113–118`

- **Q-051** [tag: mech, difficulty: easy]
  - **Q:** What does `delete(users_table)` (no WHERE) do?
  - **A:** Removes every row from the table, but leaves the schema intact.
  - **Source:** `examples/s05_delete_data.py:127–135`

- **Q-052** [tag: knowhow, difficulty: medium]
  - **Q:** What's the difference between `DELETE` (no WHERE) and `DROP TABLE`?
  - **A:** DELETE removes rows but the table itself still exists; DROP TABLE removes the table entirely (schema and all). In SQLAlchemy, `users_table.drop(engine)` performs the drop.
  - **Source:** `examples/s05_delete_data.py:136–139`

- **Q-053** [tag: mech, difficulty: medium]
  - **Q:** In `s05`, after deleting users under 25, which two rows are removed and why?
  - **A:** Dave (19) and Eve (22). Alice (30) and Carol (41) are over 25; Bob (25) was already deleted by the previous step.
  - **Source:** `examples/s05_delete_data.py:104–122`

## utils.py and presentation

- **Q-054** [tag: mech, difficulty: easy]
  - **Q:** What is the single function exported by `utils.py`?
  - **A:** `print_table(result: CursorResult, title: str = "")` — pretty-prints a SQLAlchemy result as an ASCII table via `prettytable`.
  - **Source:** `examples/utils.py:25`

- **Q-055** [tag: knowhow, difficulty: medium]
  - **Q:** Why does `print_table` exist as a shared helper instead of each script printing rows itself?
  - **A:** So all five scripts produce visually consistent output and each script's narrative stays focused on its CRUD topic — the shared helper is the convention.
  - **Source:** `examples/utils.py:6–18`

- **Q-056** [tag: knowhow, difficulty: hard]
  - **Q:** Why is `CursorResult` "single-use", and what does that mean for `print_table`?
  - **A:** A SQLAlchemy `Result` is a forward-only cursor; once consumed it can't be re-iterated. The caller must materialize via `.all()` if they need both `print_table` AND further use of the rows.
  - **Source:** `examples/utils.py:30–34`

- **Q-057** [tag: mech, difficulty: medium]
  - **Q:** Why does `print_table` set `table.align = "l"`?
  - **A:** To left-align text columns; PrettyTable defaults to centered, which is harder to scan for longer values.
  - **Source:** `examples/utils.py:46–48`

- **Q-058** [tag: mech, difficulty: easy]
  - **Q:** How does `print_table` know what column headers to print?
  - **A:** It reads them from `result.keys()`, which lists the column names in the same order as the values in each row.
  - **Source:** `examples/utils.py:38–43`

- **Q-059** [tag: convention, difficulty: easy]

- **Q-060** [tag: convention, difficulty: easy]

- **Q-061** [tag: knowhow, difficulty: medium]
  - **Q:** Why is `echo=True` left on in every script even though it makes output verbose?
  - **A:** Generated SQL is part of the lesson — seeing the SQL your Python becomes is one of the main learning outcomes.
  - **Source:** `examples/s01_create_table.py:58–61`, `docs/learn-this-project/01-knowhow-inventory.md` § "Conventions"

- **Q-062** [tag: knowhow, difficulty: medium]
  - **Q:** When a comment in the example code says "*why*, not *what*", what does that mean in practice?
  - **A:** Comments explain the design intent (why this column is unique, why we use `engine.begin` here), not the literal code action (which the code already states).
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md` § "Conventions"

- **Q-063** [tag: convention, difficulty: medium]
  - **Q:** Where does each example script's `print_table` import come from, and how does the import resolve when running from the repo root?
  - **A:** `from utils import print_table` (sibling-file import). Python adds the script's own directory (`examples/`) to `sys.path`, so the bare `utils` import resolves to `examples/utils.py`.
  - **Source:** `examples/s01_create_table.py:44`, `docs/learn-this-project/02-runbook.md` § "Common failures"

- **Q-064** [tag: knowhow, difficulty: hard]
  - **Q:** The `examples/` directory is not packaged by `pyproject.toml` (only `learn_this_project*` is). What practical consequence does that have?
  - **A:** A user who only `pip install`s the wheel would not get the example scripts; the scripts only work if you have the repo cloned.
  - **Source:** `pyproject.toml:10–14`

- **Q-065** [tag: convention, difficulty: hard]
  - **Q:** Why does the project deliberately *not* DRY-up the schema setup that's repeated in `s02`–`s05`?
  - **A:** Repetition is the lesson — beginners benefit from re-seeing the same shape (engine → metadata → Table → create_all → seed) until it's automatic. DRY here would obscure the pattern.
  - **Source:** `examples/s02_insert_data.py:42–49`, `docs/learn-this-project/01-knowhow-inventory.md` § "Conventions"

- **Q-066** [tag: knowhow, difficulty: hard]
  - **Q:** If you wanted to make the example scripts persist data across runs, which single line would you change, and to what?
  - **A:** Change `create_engine("sqlite:///:memory:", echo=True)` to `create_engine("sqlite:///./<file>.db", echo=True)` (e.g., `sqlite:///./learning.db`) — three slashes, then a relative or absolute path to a file.
  - **Source:** `examples/s01_create_table.py:61`

- **Q-067** [tag: knowhow, difficulty: hard]
  - **Q:** Why do the example scripts use `from utils import print_table` instead of `from learn_this_project import print_table`?
  - **A:** Because `learn_this_project/__init__.py` is currently empty — there's nothing to import from it. The shared helper lives in `examples/utils.py` for now.
  - **Source:** `learn_this_project/__init__.py`, `examples/utils.py`
