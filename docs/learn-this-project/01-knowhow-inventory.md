# 01 — Knowhow Inventory

> **Scope notes (set at meta-skill bootstrap).** The teaching content lives in `examples/` (`s01_*` → `s05_*`, plus `utils.py`); dependencies and the runtime contract live in `pyproject.toml`. The top-level package `learn_this_project/` is currently a skeleton (`__init__.py` is empty) — it exists only so `pyproject.toml`'s `[tool.setuptools.packages.find]` has something to discover. Treat it as out-of-scope until it gets real code.

## Project at a glance

`learn_this_project` is a beginner-oriented walkthrough of relational-database basics, taught against SQLite using **SQLAlchemy 2.0 Core** (the `Table` API, deliberately not the ORM). Five numbered scripts (`s01` → `s05`) each demonstrate one CRUD operation end-to-end (CREATE TABLE, INSERT, SELECT, UPDATE, DELETE), printing every emitted SQL statement (`echo=True`) and rendering result rows as ASCII tables (`prettytable`). Every script is self-contained: it builds an in-memory SQLite database (`sqlite:///:memory:`), redefines the same `users` table, seeds data, and runs its lesson. The audience is a learner who has read some Python but has never written SQL; the goal is to build the mental model "rows + columns + four verbs" before introducing sessions, ORMs, migrations, or persistence.

There is no application here — no entry point, no service, no CLI, no tests. The "runnable surface" is each `examples/sNN_*.py` file, executed individually with `python examples/sNN_*.py`. They share nothing at runtime: each spins up its own SQLite engine, its own `MetaData`, its own copy of the `users` table.

## Component inventory

### `examples/s01_create_table.py` — CREATE TABLE

- **What.** Defines a `users` table with four columns (`id` PK, `name` NOT NULL, `age`, `email` UNIQUE) and emits `CREATE TABLE` against an in-memory SQLite engine. Verifies the table exists by running `inspect(engine).get_table_names()` and `inspect(engine).get_columns("users")`. Then prints the empty table via `print_table` to confirm it's queryable.
- **Why.** This is the very first script a learner sees. The lesson sequence is `engine → MetaData → Table(...) → metadata.create_all(engine) → inspect → empty SELECT`. Each step is its own commented section so the learner builds a mental ladder. `inspect()` is included on purpose — it converts "the script ran without error" into "I can see the table and its columns existed", which closes the loop on the very first script.
- **Key files.** `examples/s01_create_table.py:61` (engine), `:73` (MetaData), `:102` (Table definition), `:122` (`metadata.create_all`), `:131` (inspect block), `:148` (empty SELECT).
- **Depends on.** SQLAlchemy Core (`create_engine`, `MetaData`, `Table`, `Column`, `Integer`, `String`, `inspect`, `select`); `examples/utils.py` for `print_table`.
- **Gotchas.** `:memory:` databases vanish when the process exits — that's intentional (clean slate per run) but means nothing carries from `s01` to `s02`. `echo=True` is verbose — half the script output is generated SQL, which is the *point*, not noise.

### `examples/s02_insert_data.py` — INSERT

- **What.** After rebuilding the same schema, demonstrates two insert styles: (1) `insert(users_table).values(...)` for a single row, capturing `result.inserted_primary_key` to show the auto-assigned id; (2) `conn.execute(insert(users_table), [dict, dict, dict])` for `executemany`-style bulk insert. Reads everything back with `select(users_table)` to prove the writes landed.
- **Why.** Single-row insert and bulk insert are the two patterns a learner needs in the first week. The script makes the **shape difference** explicit: with `.values()` you don't pass a list to `execute`; without `.values()` you do. Capturing `inserted_primary_key` is the canonical answer to "how do I find out the id the database picked?" — a question every beginner asks.
- **Key files.** `examples/s02_insert_data.py:75` (single insert via `.values()`), `:95` (executemany via list-of-dicts), `:118` (read-back).
- **Depends on.** SQLAlchemy Core (adds `insert`); `utils.print_table`.
- **Gotchas.** The script does NOT supply `id`. SQLite auto-assigns because `id` is `Integer + primary_key=True`, which becomes `INTEGER PRIMARY KEY` in SQLite (auto-increment). On other dialects (Postgres without `Identity`/`Sequence`, etc.) you would handle this differently — but that's a topic for later.

### `examples/s03_select_data.py` — SELECT

- **What.** Five sub-lessons in one file: (1) select all rows; (2) select only specific columns via `users_table.c.name`; (3) WHERE filter (`age > 25`); (4) ORDER BY + LIMIT (top 2 oldest); (5) four ways to consume a `Result` — `.all()`, `.first()`, `.scalar()`, and direct iteration.
- **Why.** SELECT is the single biggest topic in CRUD; learners use it every day. Splitting it into five labeled sub-lessons keeps each one ≤ 20 lines, so the learner can run the whole script and read the output as a sequence of small worked examples. The result-consumption section (`.all()` / `.first()` / `.scalar()` / iter) is included because beginners frequently call the wrong method and either pull a giant result into memory or call `.scalar()` on a multi-row query.
- **Key files.** `examples/s03_select_data.py:80` (select all), `:97` (column projection), `:118` (WHERE), `:133` (order_by + limit), `:155` (four consumption styles).
- **Depends on.** SQLAlchemy Core (uses `select`); `utils.print_table`.
- **Gotchas.** `users_table.c.age > 25` returns a SQL expression object, not a Python boolean. The comment block at `:111–117` calls this out specifically because it's the most common conceptual stumble. Bound parameters (and therefore SQL-injection safety) come from using column expressions instead of f-strings — also flagged inline.

### `examples/s04_update_data.py` — UPDATE

- **What.** Three update lessons: (1) update one row by primary key (`where(id == 1)`); (2) update multiple rows by condition (`where(age < 30)`); (3) update with a computed value (`age = age + 1`, as a SQL expression). Defines a local `print_all(label)` helper so each step's effect is visible. Reads `result.rowcount` after each statement to surface "did it actually change anything?".
- **Why.** UPDATE is the operation where beginners cause the most damage. The script repeats the rule "always WHERE" in the module docstring AND in section comments — `nullable=False` won't save you, the database will happily set every row's name to `'YOUNGSTER'`. The `age = age + 1` lesson teaches "let the database do the math" (one round-trip, atomic) instead of read-modify-write in Python.
- **Key files.** `examples/s04_update_data.py:99` (single-row UPDATE), `:120` (multi-row UPDATE), `:145` (computed UPDATE), `:71` (`print_all` helper).
- **Depends on.** SQLAlchemy Core (adds `update`); `utils.print_table`.
- **Gotchas.** `result.rowcount == 0` is a *signal* (your WHERE matched nothing), not an error — a beginner who isn't checking it can think their UPDATE worked when it didn't. The `print_all()` helper is defined inline in this file (not in `utils.py`) on purpose — it depends on the module-local `engine` and `users_table`, so factoring it would force a more complex helper signature.

### `examples/s05_delete_data.py` — DELETE

- **What.** Three delete lessons: (1) delete one row by PK; (2) delete by WHERE (`age < 25`); (3) delete every row with no WHERE clause (the dangerous form). Closing comment contrasts `DELETE` (rows go, schema stays) with `DROP TABLE` (schema also goes — `users_table.drop(engine)`).
- **Why.** Closes the CRUD loop with the operation that destroys data. The order is deliberate: PK-targeted (safest) → WHERE-targeted → no-WHERE (loaded gun). The `DROP TABLE` aside exists because beginners often confuse DELETE-no-WHERE with DROP, and the difference matters operationally (DROP requires re-running `create_all` to recover).
- **Key files.** `examples/s05_delete_data.py:97` (delete by PK), `:119` (delete by WHERE), `:140` (delete all), `:136` (DELETE-vs-DROP comment block).
- **Depends on.** SQLAlchemy Core (adds `delete`); `utils.print_table`.
- **Gotchas.** "Run a SELECT with the same WHERE first to preview" is preached in the comment at `:113–118` — that's the actual safety habit, not Python-side defensive checks. Once a transaction commits, DELETE is irreversible at this level (no undo).

### `examples/utils.py` — `print_table` helper

- **What.** A 35-line module exposing one function: `print_table(result: CursorResult, title: str = "") -> None`. It pulls column names from `result.keys()`, builds a `prettytable.PrettyTable`, left-aligns columns (`table.align = "l"`), iterates the cursor, and prints. Optional `title` adds a `--- {title} ---` banner.
- **Why.** Every example script needs to display rows. Raw tuple printing (`(1, 'Alice', 30, 'alice@example.com')`) is hard to scan. Centralizing the helper means all five scripts have visually consistent output and each script's narrative stays focused on its own CRUD topic. The shared helper *is* the convention.
- **Key files.** `examples/utils.py:25` (signature + docstring), `:40` (column extraction), `:48` (left-align decision), `:53` (row loop).
- **Depends on.** `prettytable.PrettyTable`, `sqlalchemy.CursorResult`.
- **Gotchas.** `CursorResult` is **single-use** — once `print_table` iterates it, the caller cannot read it again. The docstring calls this out. If a script needs to both display *and* re-iterate the result, it must call `.all()` first and pass the materialized list — but none of the current examples need that.

## Conventions

1. **Script naming: `sNN_<verb>_<topic>.py`.** Two-digit zero-padded sequence (`s01`, `s02`, …) so files sort in lesson order in any file browser. The verb mirrors the SQL verb being taught.
2. **Each script is fully self-contained.** Setup (engine + metadata + table + seed) is duplicated at the top of `s02`–`s05`. This is *deliberate non-DRY* — beginners benefit from re-seeing the same shape, and `:memory:` databases can't share state across processes anyway.
3. **`with engine.begin() as conn:` for writes; `with engine.connect() as conn:` for reads.** `begin()` opens a transactional block (auto-commit on clean exit, rollback on exception); `connect()` does not. Every script follows this split — see `s02:75` (write) vs `s03:80` (read).
4. **Docstring every script with: goal → mental model → why-this-choice.** Open `s01:1–31` to see the canonical shape; `s02–s05` follow the same template.
5. **One section per concept, separated by `# ---...---` banners.** Easy to grep, easy to skim, easy for a learner to set a breakpoint at the start of any section.
6. **`echo=True` always.** Generated SQL is part of the lesson; don't silence it.
7. **All output flows through `print_table`** (or its `print_all` wrapper in `s04`/`s05`). Bare `print(row)` only appears in `s03`'s "iter" example, where seeing raw row tuples is the point.
8. **Comments explain *why*, not *what*.** Code says `metadata.create_all(engine)`; the comment above explains *why this is the moment Python finally talks to the database*.

## External dependencies

- **SQLAlchemy `>=2.0.33, <3.0.0`** — the database toolkit. Chosen over raw `sqlite3` because (a) it teaches a vocabulary (`Table`, `Column`, `select`, `insert`, …) that transfers to other databases, and (b) it provides parameterized statement construction that prevents SQL injection by default. The Core layer (not the ORM) is used because it stays close to SQL while being Pythonic; ORM concepts (Session, identity map, mapped classes) are deferred. 2.0+ is required because the unified `select()/insert()/update()/delete()` constructor API is 2.0-only.
- **prettytable `>=3.15.1, <4.0.0`** — ASCII table renderer. Chosen over hand-rolling formatting in `print_table` because (a) it handles column-width calculations correctly for varying string lengths, (b) it has a stable single-purpose API (`field_names`, `add_row`, `align`), and (c) it's tiny (no transitive baggage). A `tabulate`-based alternative would be similarly fine.
- **Python `>=3.12, <4.0`** — pinned in `pyproject.toml` and `mise.toml`. 3.12 is recent-but-stable; nothing in the example code requires 3.12-specific features (would likely run on 3.10+), but pinning a single version simplifies onboarding.
