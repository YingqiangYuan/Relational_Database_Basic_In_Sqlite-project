# 05 — Interview Playbook

> **Scope notes (set at meta-skill bootstrap).** This is a *teaching project*. Treat the candidate's framing of it as the most interesting signal: do they pitch it as "a portfolio app I built" (overclaim) or as "an exercise that teaches relational DB fundamentals to me / to others"? The honest framing is much stronger; an interviewer who notices the difference learns a lot.

## Opening — the 90-second pitch (model script)

> "This project is a teaching artifact for relational-database basics, built on SQLite via SQLAlchemy 2.0 — covering both raw SQL through `sqlalchemy.text(...)` and Core Expression, deliberately stopping short of the ORM. The lessons live in `examples/01-crud-two-styles/` as **two parallel five-script series**: `s11`–`s15` teach CRUD as raw SQL strings with `:name` bound parameters, and `s21`–`s25` teach the same CRUD operations again using `Table`, `select`, `insert`, `update`, `delete`. Every script is fully self-contained — same in-memory SQLite engine, same `users` table, redefined at the top — because the repetition is part of the lesson, and `:memory:` databases can't share state across processes anyway. `examples/01-crud-two-styles/README.md` is the on-ramp doc explaining why scripts (not a GUI), why SQLite, why SQLAlchemy, and the read order. `echo=True` is on in the s2x series so the learner sees the SQL their Python generated; it's off in s1x because the SQL is already in the source. A shared `print_table` helper in `examples/01-crud-two-styles/utils.py` renders results as ASCII tables. The package `learn_this_project/` is currently an empty skeleton, kept buildable for later refactors. The next step would be a parallel ORM lesson set (`s31`–`s35`), a real `tests/` directory smoke-testing each script, and a multi-table example with foreign keys to introduce JOINs." (≈200 words)

If the candidate's pitch substantively diverges from this, that's the first signal — probe what they actually understand vs. what's narrative.

## Round 1 — what you have (mechanism, data flow, architecture)

### 1.1 Walk me through what happens when I run `python examples/01-crud-two-styles/s22_insert_data.py`. (Or `s12_insert_data.py` for the raw-SQL counterpart.)

- **Strong answer (s22, Core).** Python starts; `sqlalchemy` and the local `utils` module are imported. `create_engine("sqlite:///:memory:", echo=True)` returns an engine handle but doesn't connect. `MetaData()` creates an empty registry. `users_table = Table(...)` registers a table description on the metadata. `metadata.create_all(engine)` opens the first real connection and emits `CREATE TABLE users (...)`. Then a `with engine.begin() as conn:` block runs `insert(users_table).values(...)` for a single row, prints `inserted_primary_key`, and commits. A second `with engine.begin()` block runs `conn.execute(insert(users_table), [dict, dict, dict])` — the executemany form — for three rows. Finally a `with engine.connect():` block runs `select(users_table)` and pipes the result through `print_table`. Process exits, in-memory DB is destroyed.
- **Strong answer (s12, raw SQL).** Same lifecycle, but the schema is created via `conn.execute(text("CREATE TABLE IF NOT EXISTS users (...)"))`, the single insert uses `text("INSERT ... VALUES (:name, :age, :email)")` plus a parameter dict and reports `result.lastrowid` instead of `inserted_primary_key`, and the executemany form passes a list of dicts as the second arg to `conn.execute(text(...), [...])`. No `MetaData` or `Table` objects involved.
- **Follow-ups.** "What if I removed the `with engine.begin()` and used `engine.connect()` for the inserts — what would happen?" "Why doesn't `create_engine` connect immediately?" "Why does s12 use `result.lastrowid` but s22 uses `result.inserted_primary_key` — what's the difference?"
- **Weak answer signature.** Hand-waves "it just runs the SQL." No mention of `:memory:` lifetime, transactions, lazy connection, the executemany shape difference, or how the new-row id is recovered.

### 1.2 The `users` table has four columns. Walk me through each constraint and why it's there.

- **Strong answer.** `id Integer primary_key=True` — every row needs a unique identifier; SQLite auto-assigns next-int. `name String nullable=False` — name is required; the database rejects inserts that don't supply one. `age Integer` (nullable defaults to True) — age is optional, a user might not have provided it. `email String unique=True` — the database itself rejects duplicate emails, enforcing the invariant even if app code is buggy.
- **Follow-ups.** "Where is `nullable=True` actually written?" (it isn't — that's the default; this checks if the candidate notices). "If I removed `unique=True`, where would the duplication get caught instead?" (nowhere automatic; you'd need application-level checks, which is fragile).
- **Weak answer signature.** Lists what each constraint does without saying *why* it's the database's job, not the app's.

### 1.3 What does `with engine.begin() as conn:` actually do?

- **Strong answer.** Three things at once: opens a connection, starts a transaction, and on clean exit commits — on exception, rolls back. It's the canonical write block for SQLAlchemy 2.0 Core.
- **Follow-ups.** "And `engine.connect()`?" (no auto-transaction, suitable for reads). "What if the block raises but you catch the exception inside?" (the rollback still happens because the context manager sees the exception unwinding — but only if you actually re-raise; suppressing the exception suppresses the rollback signaling).
- **Weak answer signature.** Says "it opens a connection" and stops.

### 1.4 In `s23`, `users_table.c.age > 25` — what does Python do with that, and what gets sent to the database?

- **Strong answer.** Python doesn't evaluate it as a boolean comparison. `users_table.c.age` is a `Column` object whose `__gt__` overload returns a SQL expression node. When the surrounding `select(...).where(...)` builds the statement, that node becomes `users.age > :age_1` with `25` as a bound parameter. The database does the actual row-by-row comparison. The s1x counterpart at `examples/01-crud-two-styles/s13_select_data.py:106–110` makes the same value-binding explicit by writing `text("WHERE age > :min_age")` and passing `{"min_age": 25}` as a dict.
- **Follow-ups.** "Why does that matter for security?" (bound parameters are how SQL injection is prevented). "What if I wrote `f'WHERE age > {x}'` in a `text(...)`?" (you'd be using the `text()` escape hatch without bound parameters — losing the safety net, exactly the antipattern s12/s13 warn against). "Show me where the two series make this lesson explicit." (`s13:93–104` and `s23:105–117` both contain prominent comment blocks on the security reason.)
- **Weak answer signature.** Says "it filters rows where age is greater than 25" without acknowledging the Python-vs-SQL boundary or naming bound parameters.

### 1.5 How does `print_table` know what column headers to use?

- **Strong answer.** It calls `result.keys()` on the SQLAlchemy `Result`, which returns the column names in the same order as the row values. Those become PrettyTable's `field_names`.
- **Follow-ups.** "What happens if I `.execute()` a `select(users_table.c.name, users_table.c.age)` instead of `select(users_table)`?" (only those two columns appear). "Could I call `print_table` twice on the same result?" (no — `Result` is single-use; the second call would print zero rows).
- **Weak answer signature.** Says "from the table definition" — wrong; the helper has no reference to the `Table` object.

### 1.6 The ten example scripts (s11–s15 and s21–s25) each redefine the schema at the top. Justify or critique that decision.

- **Strong answer.** Two reasons it's correct here. (1) `:memory:` databases are per-process; `s12` literally cannot inherit `s11`'s table, and the same holds for s22 inheriting from s21. (2) The repetition is pedagogy — beginners build the schema-setup pattern into muscle memory; doing it ten times across the two series cements it. The cost is that once you understand the pattern, the duplication is noise; that's why an "elevation" version factoring schema into a shared module under `learn_this_project/` is the natural next step. Doing it from day one would defeat the lesson.
- **Follow-ups.** "When does the cost of repetition exceed the benefit?" "What concrete refactor would you do, and where would the new module live?" "Why is the repetition AT LEAST as defensible across two series as it was in a single series?"
- **Weak answer signature.** Calls it "bad practice / not DRY" without engaging with *why* it's deliberate.

## Round 2 — what you'd elevate

### 2.1 Given 3 more months, what's the single highest-leverage thing you'd add?

- **Strong answer.** A test that imports and runs each example script, asserting (a) exit code 0 and (b) that key ASCII headers appear in stdout. It's small (one `tests/test_examples.py`), it catches the "I edited s13 and forgot to update its s23 sibling" regression class — which is *the* class of bug created by maintaining two parallel series — and it enables CI. From there, a real repo-root README is the natural second move (the `examples/01-crud-two-styles/README.md` is already strong).
- **Follow-ups.** "Why tests before a README?" (because a broken example silently teaches the wrong thing — much worse than a missing README). "If you got pushback that smoke tests are too loose, what next?" (refactor scripts to expose `main()` and capture stdout — but you lose the script-as-narrative shape, so it's a tradeoff).

### 2.2 The repo uses raw SQL and Core, not the ORM. How would you add an ORM lesson set without breaking the original?

- **Strong answer.** Follow the existing naming pattern and add a third series `examples/01-crud-two-styles/s31_*.py` … `s35_*.py` using `DeclarativeBase`, `Mapped`, and `Session`. Same `users` schema, same CRUD operations the existing two series cover. Each ORM file mirrors its s2x Core counterpart so the learner can compare line-for-line at three levels of abstraction (raw SQL → Core → ORM). The shared schema can either live in `learn_this_project/schema.py` (which is the natural use of the currently-empty package) or be redefined inline to preserve the same pedagogical repetition the other two series rely on.
- **Follow-ups.** "Where do you draw the line — when does `learn_this_project/` become the canonical place vs. inline?" (after the learner has seen ≥ 1 inline version per series; after that, factoring is itself a lesson worth showing). "Why does adding a third series cost less than introducing the second one did?" (the pattern is already established; the README's framing extends naturally).

### 2.3 The repo-root `README.md` is one line. What would yours look like?

- **Strong answer.** A short pitch ("a Python learner's introduction to relational DB basics — two parallel five-script series teaching CRUD first as raw SQL via `sqlalchemy.text(...)`, then as SQLAlchemy Core Expression"); prerequisites + 4-line install (`mise trust && mise install && mise run venv-create && mise run inst`); a numbered list mapping `examples/01-crud-two-styles/README.md` first, then each `examples/01-crud-two-styles/sNN_*.py` to a one-line description; an outcomes list ("after this you can: build a table, insert / read / update / delete rows safely with bound parameters, recognize SQL injection vectors, read both styles of SQL-in-Python"); a "where next" section pointing to the ORM follow-on (`s31`–`s35`), file-backed SQLite, multi-table examples. The `examples/01-crud-two-styles/README.md` does the rationale-heavy work; the repo-root README is the *index*.
- **Follow-ups.** "Where would you put sample output?" (separate `docs/lesson-output.md` or omit — sample output drifts; better to tell readers to run the script). "Why split the README in two?" (different audiences — repo-root README is for someone scanning GitHub; `examples/01-crud-two-styles/README.md` is for someone already committed to working through the lessons.)

## Round 3 — alternatives considered

### 3.1 Why SQLite, not Postgres?

- **Strong answer.** SQLite ships with Python — zero install. For a teaching repo where the goal is "understand rows + columns + four verbs", introducing a server (Postgres) adds setup friction unrelated to the lesson. The cost: SQLite has dialect quirks (looser typing, different SQL flavors of `RETURNING`, no `ENUM`, etc.) that don't transfer 1:1. Worth the tradeoff for a beginner audience.
- **Follow-ups.** "Where would SQLite specifically mislead a learner?" (foreign keys are off by default — `PRAGMA foreign_keys = ON` is required; `INTEGER PRIMARY KEY` autoincrements without `Identity`; type affinity rather than strict types).

### 3.2 Why raw SQL via `text(...)` first, then SQLAlchemy Core — and not the ORM at all?

- **Strong answer.** The s1x series shows the learner what SQL itself looks like, with bound parameters as the safety primitive — this is universal knowledge that transfers to every language and every database. The s2x series then reproduces those same lessons in Core (`select(users_table).where(...)`), which looks like SQL with Python syntax and adds composability — you can build queries piece by piece, conditionally extend them, and the bound-parameter safety is automatic. The ORM (Session, identity map, mapped classes, attribute-level change tracking) is layered on top of Core and adds concepts the learner doesn't have yet; introducing it before they have the lower two layers reverses the natural learning gradient. Showing both raw SQL and Core means when the learner meets the ORM, they already know what SQL the ORM is generating *and* why generating that SQL in code instead of as a string is desirable.
- **Follow-ups.** "Why use SQLAlchemy at all instead of `sqlite3`?" (the SQLAlchemy expression language enforces parameterized queries by default, and the vocabulary transfers to other DBs; raw `sqlite3` invites string-formatting WHERE clauses). "What does the s1x series teach that the s2x series alone would miss?" (the ability to *read* SQL written by other people in other languages; injection mechanics seen with your own eyes via `:name`; the realization that Core *is* generating exactly this SQL).

### 3.3 Why `prettytable`, not `tabulate` or `rich`?

- **Strong answer.** `prettytable` has a tiny stable API (`field_names`, `add_row`, `align`) — exactly what `print_table` needs and nothing more. `tabulate` works equally well; `rich` is much heavier and would introduce a styling layer that's irrelevant for a beginner repo. The tradeoff is small enough that any of the three is defensible; consistency (one helper, one library) matters more than the choice.
- **Follow-ups.** "If your lesson grew to include color-coded diffs (before/after rows), would you reconsider?" (yes — `rich` becomes a fit there).

### 3.4 Why `:memory:` SQLite, not a file-backed DB the learner can re-open?

- **Strong answer.** Two reasons. (1) Every run starts from a known clean state — no stale data, no "did I already insert that?" confusion. (2) No file path, no cleanup, no .gitignore entry. The cost is that the learner never sees persistence — which is why the elevation roadmap suggests an `s30_setup_file.py` (or similar) showing file-backed SQLite explicitly.
- **Follow-ups.** "When does in-memory bite you in real teaching?" (the day someone asks "where does the data go between runs?" — and the honest answer is "this whole lesson hides that from you").

### 3.5 Why does each script repeat the schema setup instead of importing it?

- **Strong answer.** Pedagogical: beginners benefit from re-seeing the same shape (raw `CREATE TABLE` text in s1x, MetaData+Table+create_all in s2x) across every script in each series. There's a real cost (noise once you've internalized it) but the elevation path covers that — adding the ORM series `s31`–`s35` is the next opportunity to demonstrate the shared-module pattern, so the learner experiences three versions of the code at increasing levels of abstraction.
- **Follow-ups.** "What other anti-DRY patterns are pedagogical?" (test fixtures intentionally not factored; example apps that copy the same boilerplate; inline imports inside functions in tutorials).

## Round 4 — problems hit / hypothetical debugging

### 4.1 A learner runs `python examples/01-crud-two-styles/s23_select_data.py` and gets `ModuleNotFoundError: No module named 'utils'`. What happened and how do you fix it?

- **Strong answer.** They ran the script from a directory other than the project root or `examples/01-crud-two-styles/`. The import is a sibling-file import (`from utils import print_table`); Python adds *the script's own directory* to `sys.path`, so `utils` resolves only when the script is invoked normally. Fix: `cd` to repo root (or `examples/01-crud-two-styles/`) and run with `uv run python examples/01-crud-two-styles/s23_select_data.py`. Robust fix: package the helper so it's importable as `from learn_this_project.utils import print_table` — the elevation roadmap calls this out.
- **Follow-ups.** "Why does Python add the script's dir to `sys.path`?" (the `__main__` runner does it). "What about `python -m`?" (different — `-m` adds the current dir, not the script dir).

### 4.2 An UPDATE silently changed every row of the table. What went wrong, and how do you recognize it before it happens?

- **Strong answer.** The UPDATE was missing a WHERE clause. The recognition habits: (1) the docstrings of `s14` and `s24` both state the rule explicitly at the very top of the file; (2) check `result.rowcount` — if you expected 1 and got 4, that's a klaxon; (3) preview with the equivalent SELECT first ("measure twice, cut once").
- **Follow-ups.** "Same scenario but for DELETE." (Same answer — `s15` and `s25` make the parallel explicit, and `s15:97–110` / `s25:106–117` spell out the "run a SELECT first" habit in the comments.)

### 4.3 You change one example script's seed data to use the same email twice. What error do you expect, and where does it come from?

- **Strong answer.** `sqlite3.IntegrityError: UNIQUE constraint failed: users.email` — surfaced through SQLAlchemy as `IntegrityError` wrapping the underlying DBAPI error. The constraint is enforced by the database, not by Python — so even bypassing SQLAlchemy and going to raw `sqlite3` would still error.
- **Follow-ups.** "Where in the schema definition is this enforced?" (`Column("email", String, unique=True)` in each `Table` block).

## Round 5 — production pushbacks

### 5.1 If you wanted to deploy something based on this codebase, what's the first thing you'd change?

- **Strong answer.** Switch off `echo=True` in the s2x series (or gate it behind an env flag) — printing every SQL statement to stdout is great for teaching and terrible in production logs; the s1x series already has it off. Right after that, switch from `:memory:` SQLite to a real persistent database, configure connection pooling explicitly, and add structured logging via the `sqlalchemy.engine` logger instead of `echo`.
- **Follow-ups.** "What's the right way to keep `echo`-like behavior in development?" (named logger `logging.getLogger('sqlalchemy.engine').setLevel(logging.INFO)` controlled by env var).

### 5.2 Suppose this project's `users` table grew to 50M rows. What changes?

- **Strong answer.** The example UPDATE that does `users_table.c.age + 1` for every row becomes a long-running statement that locks the table — that's the classic "happy birthday for everyone" antipattern at scale. You'd batch by id range (`WHERE id BETWEEN ? AND ?`) and commit between batches. The single-call SELECT-everything `print_table(conn.execute(select(users_table)))` would also be unworkable — you'd iterate and stream. Indexes on common WHERE columns (`age`, `email` already indexed via UNIQUE) would matter.
- **Follow-ups.** "What about read-after-write consistency on the bulk update?" (depends on isolation level; SQLite's default is serializable per connection, so it's fine for single-writer; under MVCC databases like Postgres you'd think about it).

### 5.3 The dependency `prettytable` becomes unmaintained. Plan B?

- **Strong answer.** The blast radius is one file: `examples/01-crud-two-styles/utils.py`'s `print_table`. Drop-in replacement with `tabulate`, hand-rolled formatting, or `rich.table.Table` — all under 30 lines. Low coupling is a strength of the design here.
- **Follow-ups.** "How would you have known the blast radius without me telling you?" (grep for `prettytable` — exactly one import in one file).

### 5.4 Imagine a P0: somebody added a new example script that, on import, drops the `users` table. How is that even possible, and how do you prevent it?

- **Strong answer.** Each example creates its own in-memory engine, so the blast radius is one process — but the pattern is *importable*. If a downstream consumer ever does `import examples.sNN_*`, the module-level code (`metadata.create_all(engine)` etc.) runs. The fix is the universal one: guard top-level side effects with `if __name__ == "__main__":`. The current scripts don't do this — that's a known weakness of the script-as-narrative style and a candidate elevation. Note also the elevation point in `03-elevation-roadmap.md` § "Test depth" depends on this being addressable.
- **Follow-ups.** "Would you actually do that refactor for this project?" (only if tests start importing the scripts; the narrative style is currently more valuable than import-safety).
