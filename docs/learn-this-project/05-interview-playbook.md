# 05 — Interview Playbook

> **Scope notes (set at meta-skill bootstrap).** This is a *teaching project*. Treat the candidate's framing of it as the most interesting signal: do they pitch it as "a portfolio app I built" (overclaim) or as "an exercise that teaches relational DB fundamentals to me / to others"? The honest framing is much stronger; an interviewer who notices the difference learns a lot.

## Opening — the 90-second pitch (model script)

> "This project is a teaching artifact for relational-database basics, built on SQLite using SQLAlchemy 2.0 Core — deliberately not the ORM. Five short scripts under `examples/` walk through one CRUD verb each: `s01` creates a `users` table, `s02` inserts (single rows and bulk), `s03` selects (projection, WHERE, ORDER BY, LIMIT, plus four ways to consume a result), `s04` updates (single, multi-row, computed values), `s05` deletes (PK, WHERE, no-WHERE, vs DROP). Every script is fully self-contained — same in-memory SQLite engine, same `users` table, redefined at the top — because the repetition is part of the lesson. `echo=True` prints every generated SQL statement so the learner sees the mapping from Python to SQL, and a shared `print_table` helper renders results as ASCII tables. The package itself, `learn_this_project/`, is currently a skeleton — `__init__.py` is empty — kept buildable for later refactors. The next step would be a parallel ORM lesson set, a real `tests/` directory smoke-testing each script, and a multi-table example with foreign keys to introduce JOINs." (≈150 words)

If the candidate's pitch substantively diverges from this, that's the first signal — probe what they actually understand vs. what's narrative.

## Round 1 — what you have (mechanism, data flow, architecture)

### 1.1 Walk me through what happens when I run `python examples/s02_insert_data.py`.

- **Strong answer.** Python starts; `sqlalchemy` and the local `utils` module are imported. `create_engine("sqlite:///:memory:", echo=True)` returns an engine handle but doesn't connect. `MetaData()` creates an empty registry. `users_table = Table(...)` registers a table description on the metadata. `metadata.create_all(engine)` opens the first real connection and emits `CREATE TABLE users (...)`. Then a `with engine.begin() as conn:` block runs a single insert (`INSERT ... RETURNING id`), prints `inserted_primary_key`, and commits. A second `with engine.begin()` block runs an executemany INSERT for three rows. Finally a `with engine.connect():` block runs `SELECT * FROM users` and pipes the result through `print_table`. Process exits, in-memory DB is destroyed.
- **Follow-ups.** "What if I removed the `with engine.begin()` and used `engine.connect()` for the inserts — what would happen?" "Why doesn't `create_engine` connect immediately?"
- **Weak answer signature.** Hand-waves "it just runs the SQL." No mention of `:memory:` lifetime, transactions, lazy connection, or `inserted_primary_key`.

### 1.2 The `users` table has four columns. Walk me through each constraint and why it's there.

- **Strong answer.** `id Integer primary_key=True` — every row needs a unique identifier; SQLite auto-assigns next-int. `name String nullable=False` — name is required; the database rejects inserts that don't supply one. `age Integer` (nullable defaults to True) — age is optional, a user might not have provided it. `email String unique=True` — the database itself rejects duplicate emails, enforcing the invariant even if app code is buggy.
- **Follow-ups.** "Where is `nullable=True` actually written?" (it isn't — that's the default; this checks if the candidate notices). "If I removed `unique=True`, where would the duplication get caught instead?" (nowhere automatic; you'd need application-level checks, which is fragile).
- **Weak answer signature.** Lists what each constraint does without saying *why* it's the database's job, not the app's.

### 1.3 What does `with engine.begin() as conn:` actually do?

- **Strong answer.** Three things at once: opens a connection, starts a transaction, and on clean exit commits — on exception, rolls back. It's the canonical write block for SQLAlchemy 2.0 Core.
- **Follow-ups.** "And `engine.connect()`?" (no auto-transaction, suitable for reads). "What if the block raises but you catch the exception inside?" (the rollback still happens because the context manager sees the exception unwinding — but only if you actually re-raise; suppressing the exception suppresses the rollback signaling).
- **Weak answer signature.** Says "it opens a connection" and stops.

### 1.4 In `s03`, `users_table.c.age > 25` — what does Python do with that, and what gets sent to the database?

- **Strong answer.** Python doesn't evaluate it as a boolean comparison. `users_table.c.age` is a `Column` object whose `__gt__` overload returns a SQL expression node. When the surrounding `select(...).where(...)` builds the statement, that node becomes `users.age > :age_1` with `25` as a bound parameter. The database does the actual row-by-row comparison.
- **Follow-ups.** "Why does that matter for security?" (bound parameters are how SQL injection is prevented). "What if I wrote `f'WHERE age > {x}'`?" (you'd be using the `text()` escape hatch, losing the safety net).
- **Weak answer signature.** Says "it filters rows where age is greater than 25" without acknowledging the Python-vs-SQL boundary.

### 1.5 How does `print_table` know what column headers to use?

- **Strong answer.** It calls `result.keys()` on the SQLAlchemy `Result`, which returns the column names in the same order as the row values. Those become PrettyTable's `field_names`.
- **Follow-ups.** "What happens if I `.execute()` a `select(users_table.c.name, users_table.c.age)` instead of `select(users_table)`?" (only those two columns appear). "Could I call `print_table` twice on the same result?" (no — `Result` is single-use; the second call would print zero rows).
- **Weak answer signature.** Says "from the table definition" — wrong; the helper has no reference to the `Table` object.

### 1.6 The five example scripts each redefine the schema at the top. Justify or critique that decision.

- **Strong answer.** Two reasons it's correct here. (1) `:memory:` databases are per-process; `s02` literally cannot inherit `s01`'s table. (2) The repetition is pedagogy — beginners build the schema-setup pattern into muscle memory. The cost is that once you understand the pattern, the duplication is noise; that's why an "elevation" version factoring schema into a shared module is the natural next step. Doing it from day one would defeat the lesson.
- **Follow-ups.** "When does the cost of repetition exceed the benefit?" "What concrete refactor would you do, and where would the new module live?"
- **Weak answer signature.** Calls it "bad practice / not DRY" without engaging with *why* it's deliberate.

## Round 2 — what you'd elevate

### 2.1 Given 3 more months, what's the single highest-leverage thing you'd add?

- **Strong answer.** A test that imports and runs each example script, asserting (a) exit code 0 and (b) that key ASCII headers appear in stdout. It's small (one `tests/test_examples.py`), it catches the "I edited s03 and forgot to re-run it" regression class, and it enables CI. From there, a real README is the natural second move.
- **Follow-ups.** "Why tests before a README?" (because a broken example silently teaches the wrong thing — much worse than a missing README). "If you got pushback that smoke tests are too loose, what next?" (refactor scripts to expose `main()` and capture stdout — but you lose the script-as-narrative shape, so it's a tradeoff).

### 2.2 The repo uses Core, not the ORM. How would you add an ORM lesson set without breaking the original?

- **Strong answer.** Add `examples/sNN_orm.py` files alongside the existing scripts (`s02_orm_insert_data.py`, etc.) using `DeclarativeBase`, `Mapped`, and `Session`. Same `users` schema. Each ORM file mirrors its Core counterpart so the learner can compare line-for-line. The shared schema can either live in `learn_this_project/schema.py` (which is the natural use of the currently-empty package) or be redefined inline to preserve the same pedagogical repetition.
- **Follow-ups.** "Where do you draw the line — when does `learn_this_project/` become the canonical place vs. inline?" (after the learner has seen ≥ 1 inline version; after that, factoring is itself a lesson worth showing).

### 2.3 The README is one line. What would yours look like?

- **Strong answer.** A short pitch ("a Python learner's introduction to relational DB basics — five worked examples, one per CRUD verb, on SQLite via SQLAlchemy 2.0 Core"); prerequisites + 4-line install (`mise trust && mise install && mise run venv-create && mise run inst`); a numbered list mapping each `examples/sNN_*.py` to a one-line description; an outcomes list ("after this you can: build a table, insert / read / update / delete rows safely, recognize SQL injection vectors"); a "where next" section pointing to ORM, file-backed SQLite, multi-table examples.
- **Follow-ups.** "Where would you put sample output?" (separate `docs/lesson-output.md` or omit — sample output drifts; better to tell readers to run the script).

## Round 3 — alternatives considered

### 3.1 Why SQLite, not Postgres?

- **Strong answer.** SQLite ships with Python — zero install. For a teaching repo where the goal is "understand rows + columns + four verbs", introducing a server (Postgres) adds setup friction unrelated to the lesson. The cost: SQLite has dialect quirks (looser typing, different SQL flavors of `RETURNING`, no `ENUM`, etc.) that don't transfer 1:1. Worth the tradeoff for a beginner audience.
- **Follow-ups.** "Where would SQLite specifically mislead a learner?" (foreign keys are off by default — `PRAGMA foreign_keys = ON` is required; `INTEGER PRIMARY KEY` autoincrements without `Identity`; type affinity rather than strict types).

### 3.2 Why SQLAlchemy Core, not the ORM?

- **Strong answer.** Core stays close to SQL — `select(users_table).where(...)` looks like SQL with Python syntax. The ORM adds Session, identity map, mapped classes, attribute-level change tracking — all useful in real apps but layered on top of concepts the learner doesn't have yet. Showing Core first means when the learner meets the ORM, they already know what SQL the ORM is generating.
- **Follow-ups.** "Why use SQLAlchemy at all instead of `sqlite3`?" (the SQLAlchemy expression language enforces parameterized queries by default, and the vocabulary transfers to other DBs; raw `sqlite3` invites string-formatting WHERE clauses).

### 3.3 Why `prettytable`, not `tabulate` or `rich`?

- **Strong answer.** `prettytable` has a tiny stable API (`field_names`, `add_row`, `align`) — exactly what `print_table` needs and nothing more. `tabulate` works equally well; `rich` is much heavier and would introduce a styling layer that's irrelevant for a beginner repo. The tradeoff is small enough that any of the three is defensible; consistency (one helper, one library) matters more than the choice.
- **Follow-ups.** "If your lesson grew to include color-coded diffs (before/after rows), would you reconsider?" (yes — `rich` becomes a fit there).

### 3.4 Why `:memory:` SQLite, not a file-backed DB the learner can re-open?

- **Strong answer.** Two reasons. (1) Every run starts from a known clean state — no stale data, no "did I already insert that?" confusion. (2) No file path, no cleanup, no .gitignore entry. The cost is that the learner never sees persistence — which is why the elevation roadmap suggests a `s00_setup.py` showing file-backed SQLite explicitly.
- **Follow-ups.** "When does in-memory bite you in real teaching?" (the day someone asks "where does the data go between runs?" — and the honest answer is "this whole lesson hides that from you").

### 3.5 Why does each script repeat the schema setup instead of importing it?

- **Strong answer.** Pedagogical: beginners benefit from re-seeing engine → MetaData → Table → create_all → seed five times. There's a real cost (noise once you've internalized it) but the elevation path covers that — add a parallel `examples/v2/` that uses a shared module so the learner experiences both versions of the code.
- **Follow-ups.** "What other anti-DRY patterns are pedagogical?" (test fixtures intentionally not factored; example apps that copy the same boilerplate; inline imports inside functions in tutorials).

## Round 4 — problems hit / hypothetical debugging

### 4.1 A learner runs `python examples/s03_select_data.py` and gets `ModuleNotFoundError: No module named 'utils'`. What happened and how do you fix it?

- **Strong answer.** They ran the script from a directory other than the project root or `examples/`. The import is a sibling-file import (`from utils import print_table`); Python adds *the script's own directory* to `sys.path`, so `utils` resolves only when the script is invoked normally. Fix: `cd` to repo root (or `examples/`) and run with `uv run python examples/s03_select_data.py`. Robust fix: package the helper so it's importable as `from learn_this_project.utils import print_table` — the elevation roadmap calls this out.
- **Follow-ups.** "Why does Python add the script's dir to `sys.path`?" (the `__main__` runner does it). "What about `python -m`?" (different — `-m` adds the current dir, not the script dir).

### 4.2 An UPDATE silently changed every row of the table. What went wrong, and how do you recognize it before it happens?

- **Strong answer.** The UPDATE was missing a WHERE clause. The recognition habits: (1) `s04`'s docstring states the rule explicitly; (2) check `result.rowcount` — if you expected 1 and got 4, that's a klaxon; (3) preview with the equivalent SELECT first.
- **Follow-ups.** "Same scenario but for DELETE." (Same answer — `s05` makes the parallel explicit.)

### 4.3 You change one example script's seed data to use the same email twice. What error do you expect, and where does it come from?

- **Strong answer.** `sqlite3.IntegrityError: UNIQUE constraint failed: users.email` — surfaced through SQLAlchemy as `IntegrityError` wrapping the underlying DBAPI error. The constraint is enforced by the database, not by Python — so even bypassing SQLAlchemy and going to raw `sqlite3` would still error.
- **Follow-ups.** "Where in the schema definition is this enforced?" (`Column("email", String, unique=True)` in each `Table` block).

## Round 5 — production pushbacks

### 5.1 If you wanted to deploy something based on this codebase, what's the first thing you'd change?

- **Strong answer.** Switch off `echo=True` (or gate it behind an env flag) — printing every SQL statement to stdout is great for teaching and terrible in production logs. Right after that, switch from `:memory:` SQLite to a real persistent database, configure connection pooling explicitly, and add structured logging via the `sqlalchemy.engine` logger instead of `echo`.
- **Follow-ups.** "What's the right way to keep `echo`-like behavior in development?" (named logger `logging.getLogger('sqlalchemy.engine').setLevel(logging.INFO)` controlled by env var).

### 5.2 Suppose this project's `users` table grew to 50M rows. What changes?

- **Strong answer.** The example UPDATE that does `users_table.c.age + 1` for every row becomes a long-running statement that locks the table — that's the classic "happy birthday for everyone" antipattern at scale. You'd batch by id range (`WHERE id BETWEEN ? AND ?`) and commit between batches. The single-call SELECT-everything `print_table(conn.execute(select(users_table)))` would also be unworkable — you'd iterate and stream. Indexes on common WHERE columns (`age`, `email` already indexed via UNIQUE) would matter.
- **Follow-ups.** "What about read-after-write consistency on the bulk update?" (depends on isolation level; SQLite's default is serializable per connection, so it's fine for single-writer; under MVCC databases like Postgres you'd think about it).

### 5.3 The dependency `prettytable` becomes unmaintained. Plan B?

- **Strong answer.** The blast radius is one file: `examples/utils.py`'s `print_table`. Drop-in replacement with `tabulate`, hand-rolled formatting, or `rich.table.Table` — all under 30 lines. Low coupling is a strength of the design here.
- **Follow-ups.** "How would you have known the blast radius without me telling you?" (grep for `prettytable` — exactly one import in one file).

### 5.4 Imagine a P0: somebody added a new example script that, on import, drops the `users` table. How is that even possible, and how do you prevent it?

- **Strong answer.** Each example creates its own in-memory engine, so the blast radius is one process — but the pattern is *importable*. If a downstream consumer ever does `import examples.sNN_*`, the module-level code (`metadata.create_all(engine)` etc.) runs. The fix is the universal one: guard top-level side effects with `if __name__ == "__main__":`. The current scripts don't do this — that's a known weakness of the script-as-narrative style and a candidate elevation. Note also the elevation point in `03-elevation-roadmap.md` § "Test depth" depends on this being addressable.
- **Follow-ups.** "Would you actually do that refactor for this project?" (only if tests start importing the scripts; the narrative style is currently more valuable than import-safety).
