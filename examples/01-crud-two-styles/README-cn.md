# 示例代码 —— 背景介绍与阅读指南

本文件夹是整门课程的动手实践部分。在打开第一个脚本之前，请先把这一页读一遍。它解释了**这些脚本是什么**、**为什么我们这样组织它们**，以及 **每一组带编号的脚本想教你什么**。在这里花上几分钟，能省下后面大量的困惑。

## 这门课讲什么

这是一门**关系型数据库**入门课，使用 **SQLite** 作为具体的数据库引擎。目标设定得很克制、也很有意：学完之后，你应该能 *感觉* 到关系型数据库是什么 —— 表、行、列、主键、简单查询 —— 而不被周围那一大堆生态淹没。

我们不会讲服务器管理、索引策略、查询规划器、复制、生产部署。那些都是真实而重要的话题，但属于后续课程。这里我们只贴近基础，让核心概念真正扎根。

## 为什么用 Python 脚本，而不是数据库 GUI？

学 SQL 的本能反应通常是：打开一个数据库工具（DBeaver、TablePlus、 `sqlite3` shell 等等），粘贴一句 `CREATE TABLE`，再粘贴一句 `INSERT`，再粘贴一句 `SELECT`，在 GUI 里看结果。单条语句这样做没问题，但作为教学方式它很快就会崩掉：

- **难以复现。** 教程通常说"先做第 1 步，再做第 2 步，再做第 3 步"。如果你忘了自己在哪一步，或者把第 3 步跑在了第 2 步之前，数据库现在的状态就不再匹配教程了。从这里开始，每一个输出看起来都"不对劲"，而你也搞不清为什么。
- **难以重来。** 想回到干净状态，你得手动 drop 表、重新建表、重新插种子数据 —— 然后你就在调试这套清理流程，而不是在学 SQL 了。
- **隐藏了顺序。** 在 GUI 里点点点，并不强制顺序。脚本就强制了：第 1 行先于第 2 行执行，没得商量。

把每节课塞进一个小 Python 脚本，正好解决这三个问题：

- **步骤被冻结在文件里**，顺序就是课程想要的顺序。
- 每个脚本一开头就**建一个全新的内存数据库**（`sqlite:///:memory:`）。这个数据库只在脚本运行期间存在，脚本一退出就消失。下一次运行得到一个全新的数据库 —— 没有任何残留状态要操心。
- 你可以**把同一个脚本随便跑多少次**，输出都一模一样。当你想搞明白某件事的行为时，这正是你需要的属性。

所以 Python 文件并不是这节课本身 —— **里面的 SQL 才是这节课**。 Python 只是一个精确、可复现的方式，按顺序把这些 SQL 回放给你看。

## 为什么用 SQLite？

大多数"真正"的关系型数据库（PostgreSQL、MySQL、SQL Server、Oracle 等等）需要你跑一个独立的**服务器进程**、配用户、开端口、管凭据等等。对一个目标只是"我想搞明白 SELECT 到底干了啥"的人来说，那是一大堆仪式。

SQLite 把这些全跳过了。它是：

- **只是一个库。** 没有服务器，没有端口，没有守护进程。
- **只是一个文件**（或者像我们这里这样，只是一块 RAM）。整个数据库就在一个 `.db` 文件里，一条命令就能删掉。
- **标准 SQL**，对我们要教的所有内容来说都是。你在这里学到的 `CREATE TABLE`、`INSERT`、`SELECT`、`UPDATE`、`DELETE`，几乎可以原封不动地搬到 Postgres 或 MySQL 上去。
- **已经在你电脑上了。** Python 自带它。什么都不用装。

这些性质让 SQLite 成为完美的教学数据库。它在生产中嵌入式场景下也用得很广（手机 App、桌面 App、小型 Web App），所以你花在它上面的时间不是白花的。

## 为什么"学 SQL"的课里会出现 SQLAlchemy？

你会注意到这些脚本没有一个直接调用 SQLite。它们都走一个叫做 [SQLAlchemy](https://www.sqlalchemy.org/) 的库。简短解释一下为什么：

- 在 Python 世界里，如果你要认真地跟关系型数据库打交道， **SQLAlchemy 是事实上的标准**。它是 Python 生态里最成熟、用得最广、最强大的数据库工具集。
- 它还是一个 *分层* 的库。最底层让你直接发原始 SQL 字符串。再往上一层让你用 Python 表达式构造 SQL。最顶层（ORM）让你把数据库行当成 Python 对象。我们会用底下两层，忽略最上面那层。
- 它替我们处理了大量不光鲜但很重要的细节：连接管理、事务、安全的参数绑定、不同数据库的方言差异。即便我们写原始 SQL，走 SQLAlchemy 也能让代码更干净、更安全。

对这门课来说，你只需要知道：**SQLAlchemy 是我们走进数据库的那扇门。它存在、它很强大，你现在不需要精通它。**

## 两个脚本系列：`s1x_*` 和 `s2x_*`

带编号的示例脚本分成两个平行系列。它们覆盖完全一样的 SQL 主题（`CREATE`、`INSERT`、`SELECT`、`UPDATE`、`DELETE`），但展示了把这些 SQL 送进数据库的两种不同 *风格*。你应该先读 s1x，再读 s2x，按顺序来。

### 系列 1 —— `s11_*` 到 `s15_*`：原始 SQL（通过 `text("...")`）

这些脚本让你像在数据库 shell 里写 SQL 一样写它 —— 就是一个普通字符串：

```python
conn.execute(text("SELECT * FROM users WHERE age > :min_age"),
             {"min_age": 25})
```

这个系列存在的理由是：**在你能欣赏对 SQL 的任何抽象之前，你得先看到 SQL 本身**。如果我们直接跳到"用 Python 对象搭出查询"的风格，你会很难看出哪一段 Python 对应哪一段 SQL，那层抽象就会感觉像魔法。

读这些脚本时有两点值得注意：

1. 传给 `text("...")` 的那个字符串 *就是* SQL —— 上面没有任何翻译层。把它复制到 `sqlite3` shell 里，原封不动就能跑。
2. 那些冒号开头的 `:name` 占位符是**绑定参数**。永远不要靠拼字符串或者 f-string 来用用户输入构造 SQL；那样会让你撞上 SQL 注入。 `:name` 这种形式让数据库驱动安全地处理那个值。

### 系列 2 —— `s21_*` 到 `s25_*`：SQLAlchemy Core 表达式

这些脚本再覆盖一遍同样的 SQL 主题，但这次 SQL 是用 **Python 表达式** 搭出来的，而不是当字符串敲出来的：

```python
stmt = select(users_table).where(users_table.c.age > 25)
conn.execute(stmt)
```

看起来比原始 SQL 版本更花哨，对 *单条* 查询来说说实话也不算赢 —— 你完全可以争辩说原始字符串更清楚。那为什么这种风格存在？为什么几乎所有正经的 Python 应用最后都用这种风格写 SQL？

#### 为什么真实应用里很少手写 SQL

想象你的应用对同一个 `users` 表有一百条查询。每一条都只在细节上有点差异：这一条按年龄过滤、那一条按名字过滤、又一条按年龄 **和** 城市一起过滤，并且只在用户点了某列表头时才加 `ORDER BY`。马上几个问题就冒出来：

1. **组合爆炸。** 如果每个变体都写成一个原始字符串，你最后会有几十条几乎一模一样的 SQL 字符串散落在代码各处。改个表名，你得追完每一条。
2. **条件片段很别扭。** "只在用户选了某个城市时才加 `WHERE city = :city`" 用字符串拼接来做很痛苦，而正是在这种场景下，人们容易忍不住写出 `f"... WHERE city = '{city}'"` —— 那是经典的 SQL 注入 bug。
3. **得不到语言层的帮助。** 一个普通字符串对你的编辑器、类型检查器、 linter 都是不透明的。列名拼错只在运行时、查询失败时才暴露出来。

Core 表达式风格把查询当成一个**值**来处理，让你在普通 Python 代码里一块块搭起来，这正好对症下药：

- 只在某些情况下要某个过滤？包一个 `if`： `if city: stmt = stmt.where(users_table.c.city == city)`。
- 想跨多条查询复用一段？赋给一个变量，复用那个变量。
- 想要参数安全？免费送 —— `users_table.c.age > 25` 在底层永远变成一个绑定参数，永远不是字符串拼接。
- 列名拼错？你引用 `users_table.c.aeg`，Python 立刻报错，而不是 MySQL 在凌晨 3 点抱怨。

这就是为什么生产代码库很少把 SQL 写成原始字符串：他们需要 *组合* 查询，而不是只 *运行* 查询。

#### "Core" 是什么意思，为什么看起来有点抽象？

我们在这个系列里用到的 Python 对象 —— `Table`、`Column`、`select`、 `insert`、`update`、`delete`、`where`、`values`…… —— 就是 SQLAlchemy 的 **Core 表达式语言**。它们是 Python 里一套小巧的、SQL 形状的词汇。每次调用返回一个查询 *对象*；什么都不会发给数据库，直到你 `conn.execute(stmt)`。

这就是为什么 s2x 的代码看起来比 s1x 稍微抽象一点。你不是在直接写 SQL；你是在写 *一份对 SQL 的描述*。SQLAlchemy 会把这份描述编译成 SQL，对应到你连的那个数据库。回报是可组合性；代价是多一层间接，需要稍微适应一下。

## 顺便说一句 ORM（以及这门课为什么不用它）

你可能听过 **ORM**（"Object-Relational Mapper"，对象关系映射）。 SQLAlchemy 有一套自己的 ORM，而且非常出色。ORM 让你把数据库行当成完整的 Python 对象：`user.name`、`user.email`、`session.add(user)` 等等。

ORM 解决的是一个跟 Core 表达式 *相关* 的问题 —— 它也是避免原始 SQL 字符串散落在代码里的另一种方式，也是让数据访问更结构化、可复用的方式 —— 但它带来了额外的概念（映射类、session、身份映射、惰性加载），我们这里有意不需要这些。

这门课是你第一次接触关系型数据库。目标是 *感觉* 到表和 SQL，而不是在它们之上再学一个对象框架。所以我们不用 ORM。你只需要知道它存在；等你对原始 SQL 和 Core 表达式都自如了之后，下一步自然就是它。

## 怎么运行这些示例

从项目根目录：

```bash
mise run inst                       # 一次性：安装依赖
uv run python examples/01-crud-two-styles/s11_create_table.py
uv run python examples/01-crud-two-styles/s12_insert_data.py
# ……一路跑到 s15，然后是 s21..s25
```

每个脚本都是**完全自包含的**。它会建一个全新的内存数据库、重建表、重新插入需要的种子数据，然后演示一个主题。你可以单独跑任何一个脚本，得到完整、可复现的结果。你也可以乱序跑而不必担心搞坏什么 —— 这里根本没有什么持久化的东西可以搞坏。

## 建议阅读顺序

1. 这份 README（你现在在这）。
2. `s11_create_table.py` → `s12_insert_data.py` → `s13_select_data.py` → `s14_update_data.py` → `s15_delete_data.py` （基础的 *原始 SQL* 之旅）。
3. `s21_create_table.py` → `s22_insert_data.py` → `s23_select_data.py` → `s24_update_data.py` → `s25_delete_data.py` （同样的基础，*Core 表达式* 版的一遍 —— 这一遍你会看到那层抽象到底买到了什么）。
4. 如果你好奇那些漂亮打印的表是怎么出来的，看一下 `utils.py`。它很小。

这些足够给你一个真实、可用的关系型数据库手感。等你在这里待得自如了，就可以毕业到一个基于服务器的数据库（比如 PostgreSQL），再往后是 ORM。
